Run [OpenCode](https://opencode.ai) in your browser. Install the `opencode` v2 CLI, open `localhost:3000`, done. Works on desktop browsers, tablets, and phones as a PWA.

Full project overview, screenshots, and all features: [github.com/yee94/yuri](https://github.com/yee94/yuri)

## Repository HMR development

From the repository root, run `bun run dev:web:hmr` (or start it in tmux with
`tmux new-session -s vite 'bun run dev:web:hmr'`). Open `http://127.0.0.1:5180`;
the API listens on port 3902. The supervisor restarts a crashed Vite or API
independently, with a 1–10 second backoff for repeated failures. On macOS it
cleans up the failed process group before restarting, including descendants
whose launcher has already exited. Ctrl-C stops both groups and cancels retries.
Logs remain in the tmux pane. Restarting preserves Vite's dependency cache;
`YURI_VITE_FORCE=1` remains an explicit cache-reset option.

## Install

```bash
curl -fsSL https://raw.githubusercontent.com/yee94/yuri/main/scripts/install.sh | bash
```

Or install manually: `bun add -g @yuriai/web` (or npm, pnpm, yarn).

> **Prerequisites:** [`opencode`](https://opencode.ai/v2/docs/) v2 CLI installed (PATH or `OPENCODE_BINARY`; 1.x versions are rejected), Node.js 22+.

## Usage

By default, Yuri connects to the official shared OpenCode background service used by Desktop and TUI. Closing Yuri leaves OpenCode running, and the next launch reuses it. If the service cannot start, Yuri reports the failure for retry instead of launching a private fallback. On macOS/Linux, automatic CLI discovery follows the user's interactive login-shell PATH; explicit settings/environment overrides take precedence. In-app upgrades of a shared global installation run that selected CLI's `upgrade` command, verify its on-disk version, then restart the shared service through the same CLI entry path. Homebrew symlinks remain entry paths rather than being pinned to a Cellar version. Owned-cache installations continue to use the cache installer. Failed global upgrades never silently switch to a private cache.

Explicit `OPENCODE_HOST` / `OPENCODE_PORT` connections keep their existing behavior. `YURI_OPENCODE_SHARED_SERVICE=0` selects the private managed lifecycle when required by an existing deployment.

When no usable OpenCode is installed, Yuri resolves the latest stable 2.x release (falling back to its tested pin when lookup fails), downloads the native CLI into its data directory, and configures the user's shell PATH. Open a new terminal to use `opencode`. Existing global CLIs are reused; owned cached versions remain usable offline. Shell setup failures are logged separately and retried at the next startup.

```bash
yuri                          # Start on port 3000
yuri --port 8080              # Custom port
yuri --lan --port 3000        # Listen on LAN (0.0.0.0)
yuri --ui-password secret     # Password-protect UI
yuri startup enable           # Start at login as a native service
YURI_UI_PASSWORD=secret yuri startup enable # Save service password env
yuri startup status           # Show startup service status
yuri startup disable          # Remove startup service
yuri connect-url --port 3000  # Add this server to Yuri Desktop
yuri connect-url --server http://host:3000 --qr
yuri connect-url --port 3000 --qr
yuri logs                     # Follow latest instance logs
OPENCODE_PORT=4096 OPENCODE_SKIP_START=true yuri                    # Connect to external opencode v2 server
OPENCODE_HOST=https://myhost:4096 OPENCODE_SKIP_START=true yuri  # Connect via custom host/HTTPS
yuri stop                     # Stop server
yuri update                   # Update to latest version
```

`startup enable` snapshots your current environment into the native service so startup behaves like you launched `yuri` from the same shell. This preserves provider tokens, PATH, SSH agent settings, and other CLI auth/config env vars. Use `--no-env-snapshot` for a minimal service env.

## Self-hosted Private Relay

Run a private Relay when Yuri Hosts need outbound-only remote access:

Install and run Yuri Hosts with `@yuriai/web`. Install the self-hosted Relay server separately:

```sh
npm install -g @yuriai/relay-server
yuri-relay --public-url wss://relay.example.com/ws
```

Use TLS at a reverse proxy and keep the default loopback listener. From the repository root, Docker deployment uses:

```sh
YURI_RELAY_SERVER_PUBLIC_URL=wss://relay.example.com/ws \
YURI_RELAY_PUBLISHED_PORT=8787 \
docker compose --project-directory . -f deploy/relay/docker-compose.relay.yml up -d --build
```

Compose publishes `127.0.0.1:${YURI_RELAY_PUBLISHED_PORT:-8787}` by default. `YURI_RELAY_PUBLISHED_PORT` selects the host port, and a TLS reverse proxy provides the public `wss://` entry point.

Point every Yuri Host at the Relay, then generate a Relay pairing link or enable Relay pairing:

```sh
YURI_RELAY_URL=wss://relay.example.com/ws yuri
```

The **Add a device** dialog requires a configured `ws://` or `wss://` Relay endpoint. No hosted Yuri endpoint is assumed before ownership and deployment are verified. The Host persists the selected endpoint before creating the QR code; `YURI_RELAY_URL` remains authoritative when set. The creating client remembers the last effective endpoint locally.

Saved pairing candidates retain their endpoint snapshot, including the Relay URL. Mobile and Desktop clients reconnect through that saved endpoint until a new pairing flow replaces it. See [Yuri Relay Server](https://github.com/yee94/yuri/tree/main/packages/relay-server#readme) for bundle builds, reverse-proxy configuration, security, operations, and systemd guidance.

### Connect other Yuri apps

Use `connect-url` when a web/API server should be added to Yuri Desktop or another Yuri app. If no server is running on the selected port, Yuri starts one first.

```bash
yuri connect-url --port 3000
yuri connect-url --port 3000 --qr
yuri connect-url --port 3000 --json
yuri connect-url --port 3000 --name "Workstation"
yuri connect-url --port 3000 --lan --server http://workstation.local:3000 --qr
```

### Headless/API-only server for Desktop

Use this on a remote machine when you want Yuri running as a web/API server, then connect to it from Yuri Desktop on another machine:

```bash
yuri connect-url --port 3000 --api-only --lan --server http://workstation.local:3000 --qr --ui-password your-password
```

`--api-only` starts API routes without serving browser UI assets. `--lan` binds the server so other machines can reach it. `--server` is the address saved into the Desktop connection link. `--ui-password` protects browser access if UI routes are enabled elsewhere; the generated client token is what Desktop uses for API access.

This creates a remote client token and prints an `yuri://connect?...` link. The link contains the server URL, token, label, and payload version. In Yuri Desktop, paste it in **Settings -> Remote Instances -> Direct Instances -> Import Link** to add that server as an Instance.

If the server was started with `--lan` or `--host 0.0.0.0`, `connect-url` automatically advertises a detected LAN IP instead of `127.0.0.1`. Use `--server <url>` when you want to advertise a specific DNS name, Tailscale address, reverse proxy URL, or HTTPS endpoint.

If you are exposing the server beyond localhost, start it with a password:

```bash
yuri serve --lan --port 3000 --ui-password your-password
```

Generating a client token does not automatically password-protect the hosted browser UI. `--ui-password` protects browser access; the client token lets another Yuri app connect to this server.

<details>
<summary>Connect to external OpenCode server</summary>

The external host must be **OpenCode v2**. Yuri runs v2 health (`GET /api/info`) and V1 migration (`GET /api/experimental/migration/v1`) checks; a 1.x server will not pass. Automatic discovery uses the official `opencode` command only. `OPENCODE_BINARY` and `settings.opencodeBinary` can override the executable path; admission is checked by version.

```bash
OPENCODE_PORT=4096 OPENCODE_SKIP_START=true yuri
OPENCODE_HOST=https://myhost:4096 OPENCODE_SKIP_START=true yuri
```

| Variable | Description |
|----------|-------------|
| `OPENCODE_HOST` | Full base URL of external OpenCode v2 server (overrides `OPENCODE_PORT`) |
| `OPENCODE_PORT` | Port of external OpenCode v2 server |
| `OPENCODE_SKIP_START` | Skip starting embedded OpenCode server |
| `YURI_OPENCODE_HOSTNAME` | Bind hostname for managed OpenCode server (default: `127.0.0.1`, use `0.0.0.0` for LAN/remote access — trusted networks only) |
| `YURI_HOST` | Bind hostname for the Yuri web server (default: `127.0.0.1`; use `0.0.0.0` for LAN/remote access — trusted networks only) |
| `YURI_VERBOSE_REQUEST_LOGS` | Set to `true` to log every HTTP request; disabled by default to keep user logs small |
| `YURI_SKIP_API_COMPRESSION` | Set to `true` to disable gzip compression for `/api/*` responses |
| `YURI_COMPRESS_API` | Set to `true` to force `/api/*` compression, or `false` to disable it. Desktop runtime disables API compression by default to reduce local sidecar CPU use |

</details>

<details>
<summary>systemd service (VPN / LAN access)</summary>

Use `--foreground` to keep the CLI process alive so systemd (or any other process manager) can track and restart it. Combine with `OPENCODE_HOST` to connect to an OpenCode v2 instance running as a separate service.

**`~/.config/systemd/user/opencode.service`**
```ini
[Unit]
Description=OpenCode 2 Server

[Service]
Type=simple
ExecStart=opencode serve --port 4095
Environment="PATH=/home/linuxbrew/.linuxbrew/bin:/home/linuxbrew/.linuxbrew/sbin:/home/YOU/.local/bin:/home/YOU/.npm-global/bin:/usr/local/bin:/usr/bin:/bin"
Environment=SSH_AUTH_SOCK=%t/ssh-agent.socket
Restart=on-failure
RestartSec=5

[Install]
WantedBy=default.target
```

> **Why set `PATH` and `SSH_AUTH_SOCK`?**
> systemd user services start with a minimal environment — no shell profile is sourced.
> Without an explicit `PATH`, OpenCode won't find tools installed via Homebrew, npm, or `~/.local/bin`.
> Without `SSH_AUTH_SOCK`, git operations over SSH (push, pull, clone) will fail.
> `%t` expands to `$XDG_RUNTIME_DIR` (e.g. `/run/user/1000`), where most SSH agents write their socket.

**`~/.config/systemd/user/yuri.service`**
```ini
[Unit]
Description=Yuri Web Server
After=opencode.service

[Service]
Type=simple
ExecStart=yuri serve --port 3000 --host 0.0.0.0 --ui-password your-password --foreground
Environment="OPENCODE_HOST=http://localhost:4095"
Environment="OPENCODE_SKIP_START=true"
Restart=on-failure
RestartSec=5

[Install]
WantedBy=default.target
```

```bash
systemctl --user daemon-reload
systemctl --user enable --now opencode yuri
```

`--host 0.0.0.0` is required to listen on all interfaces (the default is `127.0.0.1`). Use `--host <ip>` or `YURI_HOST=<ip>` to bind to a specific interface instead.

</details>

## Tests

Run `bun run --cwd packages/web test` from the repository root. The command
checks the Node-compatible SQLite binding before running Vitest.

`test/setup.js` makes Supertest 7.2 request the test listener's address family.
This prevents ephemeral IPv6 test listeners from accidentally reaching a real
IPv4 application on the same port, notably on macOS. The dual-listener regression
in `test/supertest-loopback.test.js` covers the routing contract. Remove the
workaround when the installed Supertest version handles this contract itself.
Plugin fixtures isolate both `OPENCODE_CONFIG` and `OPENCODE_CONFIG_DIR`, then
restore the inherited environment; custom configuration does not replace the
global configuration discovery layer.
