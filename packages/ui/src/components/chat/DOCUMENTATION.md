# Chat components

`ChatInput` owns the complete composer DOM for primary chat and explicit chat surfaces. `chatInputSurface.ts` defines a discriminated primary/secondary contract with stable surface and draft identity, active state, session and directory, selection flush/capture, scoped model/agent/variant catalog readiness, typed backend operations, command policy, activity, delivery target, and scoped composer resources. Selection values carry provider, model, agent, and variant; catalogs carry variants for that selected model plus their readiness state. Secondary model controls and mobile agent cycling consume the surface catalog, keeping workspace catalogs isolated from global configuration.

Primary selection ownership: ModelControls always receives the surface `selectionAdapter`, so session restore is coordinated by primary `ChatInput` (not ModelControls). On session/messages/catalog/config-scope change, primary resolves history (latest user message agent/provider/model/variant) then same-client selection-store memory, applies via `applyPrimaryComposerSessionRestore` (session memory only — never Project/global `saveAgentModelSelection` / `lastUserSelection`). Restore effect and flush both require `activeDirectoryKey === getConfigDirectoryKey(sessionDirectory)` so a Project B session never writes into Project A's active config; flush activates the session directory when needed, then awaits `ensureSessionRenderable` with that directory and re-validates runtime generation/transport/session/session-directory/active-config-key/edit revision before apply. Explicit user picks use `applyPrimaryComposerSelectionChange` and bump an edit revision so in-flight flush cannot overwrite them (writes Project + global last unit pick). After flush, primary send/queue capture reads live `useConfigStore.getState()` (scoped by session Project key); secondary continues surface selection values. New queue admission requires a complete `sendConfig` (providerID+modelID) and keeps composer resources when capture fails; legacy rows missing `sendConfig` may still resolve live fallback at dispatch. Queued items with `sendConfig` keep that capture and skip flush when queued-only.

Every backend request pins surface ID, transport identity, runtime generation, session, and directory **before** selection flush so a mid-flight Session switch cannot retarget the body. Primary `backend.send` rejects stale runtime generation/transport (restoreFailedSubmission path), and injects request `sessionId`/`directoryHint` into `sendMessage` for existing sessions while draft `sessionID=null` keeps materialization. Captured provider/model/agent/variant stay first-submit authoritative. Server-queued Assistant items retain required compiled `deliveryParts`; queued dispatch uses `backend.sendQueued` with captured queue scope.

Every surface supplies a stable `DraftKey`; `surface` draft owners isolate secondary drafts and attachments from primary session and new-draft keys. Primary attachments subscribe to `draftAttachmentViews` for that DraftKey (not legacy `attachedFiles`). Attachment mutations go through `createDraftAttachmentResourceAdapter(draftKey, getInput)` — an explicit DraftKey binding that never routes via `activeAttachmentDraft`. Root attachment mutations (add/remove/clear/replace/restore/VS Code) share a module-level per-`draftKeyString` serial lane across factory instances so clear→restore across factory instances stays ordered; `replaceRootAttachments` / `clearRootAttachments` / `restoreRootAttachments` use one `replaceDraftRootAttachments` CAS (no multi-step remove+add). `clearRootAttachments` and surface `clearAttachments` return `Promise<boolean>` that is true only for `status=committed && current=true` (exception/failed/conflict/stale → false). `restoreRootAttachments` / surface `restoreAttachments` enter the same lane, read **live** root DraftRecord + views, merge failed snapshot with live extras by attachmentID (`[failed..., live extras...]`), then one CAS replace so concurrent user adds during send are preserved. Submit awaits root clear before backend/send when non-queued, non-resource-preserving, and captured root attachments exist; clear false blocks send, runs full restore (queue/body/synthetic/inline + attachment merge), and toasts sendFailed. Send/command failure paths `await`/`void` async restore so unhandled rejections cannot strand resources. Queue admission (server and legacy) stages a stable admission identity and clears the composer body synchronously after claiming flight and before the first await (`selection.flush`) — same optimistic policy as direct send. Current best-effort policy: direct submit and legacy queue admission use captured attachment views immediately. Attachment clear, failed-send restore, and queue cleanup results stay outside the send/admission gate. Sent chips clear from memory while persistence continues in the background; restoration errors are allowed.

Queue actions use server admission after authoritative active or paused ownership for the current transport, including a lagging `probing` cutover publication. Shadow, blocked, wrong-transport, and otherwise unconfirmed ownership keep queue mutations frozen; a busy Composer submit falls back to captured-session `steer` so the running turn remains interactive. Submission identity gates still disable unsafe targeting. An in-flight queue admission is visible and permits later send, admission, edit, remove, manual promotion, and reorder actions. Composer `submissionFlightKind='queue'` keeps the floating queue control visible with a queuing spinner (`queuingMessageAria`) after the body clears so admission still feels immediate. Pending-admission chips show spinner plus `chat.queuedMessage.queuing` text until the authoritative row replaces them. After server admission commits, body consumption compares the captured Composer document with the current live document rather than DraftRecord object identity or persistence timing; identical delayed hydration cannot restore an admitted body, while any continued authored edit changes the document fingerprint and remains in the Composer. Attachments and inline drafts retain their independent occurrence/fingerprint checks.

`ChatContainer` accepts an optional `host` (`chatContainerHost.ts`) for embedded transcripts. Hosted mode skips the primary session-view cache, injects session/directory/composer surface/`SessionSurfaceContext`, merges `onRevertMessage` into that surface so message actions and the timeline restore into the host draft partition, and disables primary-only draft/prompt-navigator/return-to-parent features unless explicitly re-enabled.

A primary staged message edit is visible on its own row before send: `ChatMessage` reads `stagedMessageEdit` / `messageEditCommitting` from the session UI store and `MessageBody` replaces that user row's action group — keeping the row geometry — with a highlighted `editStaged` label plus a cancel affordance, then with a shimmering `editing` label once the commit is in flight. Neither state hides or removes any existing row, so the optimistic user row for the resend paints independently. Staging is disarmed by the row's cancel affordance, by leaving the session, and by the Composer losing focus. An empty Composer is explicitly **not** a disarm signal: dispatch clears the body before the send reaches `commitMessageEdit`, so treating empty as cancel drops the very edit being submitted — the edited turn survives, the resend lands as an extra message, and the `editing` paint is never released. `resolveStagedEditBlurDisarm` in `stagedMessageEditDisarm.ts` decides the blur case one tick after `onBlur`, because it needs where focus landed and because editing a second row blurs before it re-stages; it keeps the edit when the staged row changed during that tick, while a submit is in flight, inside the mobile held-focus / open-overlay windows, and when focus stayed in Composer chrome (`[data-chat-input]`, `[data-chat-input-footer]`, open dropdown content) — which covers the desktop send button and the attach / model / dictation controls. A disarmed edit makes the next send an ordinary message that deletes nothing. Staging focuses the Composer textarea once per staged row (retried on the next frame when the node is not yet mounted or still disabled) so the restored text can be edited without a second tap. The paint is released by the commit, by the settle of the send promise, and by the non-handoff `finally`, and `endMessageEditCommit` only clears a matching session/message pair, so the redundant releases are safe.

Hosted continuous Assistants inject `onEditMessage` so sent-message edit stages into the surface `DraftKey` (`surfaceDraftKey`) and a per-assistant entry owned by `assistantStagedMessageEdit.ts`. The registry scopes entries by `transport + assistantID`, serializes stage and best-effort rollback cleanup per scope, and keeps primary `stagedMessageEdit` untouched. Assistant send synchronously clears its staged marker and delivers the restored Composer content as a new message through the ordinary path. Runtime and binding changes may attempt CAS rollback in the background; failures retain the restored draft until a later user action replaces or clears it. Assistant `resources.attachments` project root DraftRecord attachments only; synthetic parts restore merge by partID and never double-send via root attachments.

Assistant send clears the staged restoration marker and follows the ordinary delivery path. Restored content is sent as a new message, so staged history mutation cannot block delivery.

History segments remain read-only (`mutateSession: false` on source-scoped surfaces). Stateless Assistants omit `onEditMessage`.

Hosted Assistant history uses the Assistant HTTP infinite query instead of per-session sync materialization. Its key and request closure capture transport identity plus runtime generation, and validate currentness before and after every page request. It preserves server `Message`/`Part` references plus source session and nullable directory while adding semantic session dividers ahead of the live binding. Each historical message with a source session receives a source-scoped read-only `SessionSurfaceContext`; known directories scope file paths, tool actions, and source-session navigation to the archived workspace, while unknown legacy directories keep these directory-dependent actions unavailable. The shared timeline controller loads current-session sync history first and then asks the host for the next Assistant history page, so desktop near-top loading and the mobile button share one completion/loading signal through small and empty cursor pages.

Hosted surfaces may provide stable-ID pending user-message presentations. `ChatContainer` appends each pending row through the standard MessageList path, keeps it visible across host binding changes, and lets an authoritative current/history row with the same message ID replace it. Assistant admission atomically rebinds that pending identity to a stateless result session, then runs bounded background materialization retries. Admission success remains final for the Composer; materialized IDs or the bounded retention deadline release pending attachment data. Rejected admission removes its pending row while the Composer restores the captured submission. Assistant session loading uses `ensureSessionRenderable` as its single authoritative materialization path.

On mobile, only the Composer is an explicit Session-swipe surface: left switches to the next ranked Session and right switches to the previous ranked Session. The transcript's right-to-left gesture presents the Session List half-sheet; code blocks and horizontal scrollers retain their own gestures. Capacitor phone nested-session entries push through the mobile navigation store; iPad, VS Code, embedded, and desktop surfaces retain their established navigation owners. The phone stack stores lightweight route metadata at arbitrary depth and renders only the top transcript plus its read-only immediate predecessor, each bound to a page-local `SessionSurfaceContext` without the primary retained-view cache. The active page retains primary capabilities. Its predecessor keeps transcript DOM and message snapshots while pausing streaming presentation, auto-follow observers, and global scroll/keyboard listeners. Phone page-back is owned by the shared native navigation driver: iOS recognizes the physical left edge and Android supplies Predictive Back progress. Hosted H5 registers no page-back touch gesture. Because the phone chat subtree mounts after navigation, the transcript and Composer Session gesture Hooks re-bind from the active secondary-page state.

Mobile direct-send keeps the Composer textarea focused so the keyboard remains available for consecutive messages. Only controls that intentionally open another mobile panel or sheet explicitly blur the textarea.

`QueuedMessageChips` roots the queue surface with `oc-composer-queue` and uses compact mobile control sizes. Those sizes only stick under real touch when `mobile.css` opts the cluster out of the global `:root.mobile-pointer` 36px button min — React `isMobile` alone is not enough. See `packages/ui/src/styles/DOCUMENTATION.md` (`isMobile` vs `mobile-pointer`) before debugging queue chip spacing that changes when DevTools inspect opens or closes.

Streaming assistant and reasoning rendering reads `streamingRenderCadence.ts`: Android native uses a 100ms source throttle and 128ms Markdown reveal pace; web, desktop, VS Code, and iOS use 20ms and 64ms. Finalized content renders immediately.
