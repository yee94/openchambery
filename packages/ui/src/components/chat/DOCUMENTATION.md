# Chat components

## Scroll hot-path boundary

Message hover chrome uses `lib/messageHover.ts` boundary handlers and the
`data-message-hovered` scope marker. The handlers write only that DOM attribute;
pointer movement must not publish React state or subscribe to scroll. Newly
streamed footer leaves inherit the current marker. Touch does not arm hover.
`index.css` targets the timestamp/actions leaves explicitly. Do not restore
ancestor `group-hover` or descendant `:hover` rules around rich message bodies:
Chromium invalidates the entire descendant tree on pointer-boundary changes,
including boundaries crossed by scrolling under a stationary pointer. Keep
generic `group` scopes local to individual attachment/code controls.

`styles/desktopTyping.chrome.test.ts` compiles production CSS and reads the
production message classes/handlers, then crosses 5,000-node message boundaries.
The style-recalculation guard is fewer than 100 elements per update, independent
of machine speed. Content DOM, selection, height, and scroll ownership remain
with their existing owners; this boundary does not unmount or defer content.
`markstreamStyles.chrome.test.ts` additionally replays 60 live Markdown updates
while scrolling across settled history, requiring stable history DOM/height,
all 60 output items, and p95 frame intervals below 50ms in production Chromium.

## Direct-send inbox presentation

Composer inbox chips exclude identities already present in the current primary
transcript, including optimistic user rows. Prompt admission and enqueue events
can precede consumption; that gap must not flash a second copy in the queue.
The inbox ledger remains intact for authoritative reconciliation and recovery.
Pending items without a transcript row still appear normally. This projection
reuses the existing session-message subscription and skips transcript work when
the inbox is empty. `ChatInput.hooks.test.tsx` covers admission, consumption and
pending recovery through the production projection.

## Mobile composer height snaps

Web composers with text expose the shared height handle (native iOS composer is excluded).
`MobileComposerHeightHandle` is a memoized leaf mounted only while that handle is
available. It receives a stable textarea ref, DraftKey string, translated label and
the parent's stable manual-height setter, never draft text. Snap/viewport Hooks and
DOM mode attributes live in that leaf; it publishes height ownership only on discrete
interaction transitions. Ordinary typing performs zero leaf Hook/effect/listener work.
`useMobileComposerSnap` owns draft-local `auto`, `min`, and `full` positions: existing
eight-line autosize, the empty textarea minimum, and the available space below the
conversation navigation. The absolute handle sits inside the card's top padding;
the handle fits within the existing 10px top inset without changing textarea padding or card height, and
the mobile status row has no extra bottom margin, whether or not the handle is present. Full mode
reaches the header's bottom edge. Visual viewport resize/scroll recomputes full
height without changing the selected mode. Native shell `yuri:keyboard-settled` also
recomputes full height after keyboard layout is applied: resize-none WebViews do not
emit a visual viewport resize when the shell shrinks. Clearing text or switching DraftKey resets
to auto. Full mode and active resizing pin the existing compact/expanded swap.

`useHeightSnap` owns pointer capture, coalesced height writes, cancellation, snapping,
and reduced-motion-aware settlement for both composers and sheets. The same textarea
stays mounted. `useComposerTextareaAutosize` yields height ownership during dragging
and manual modes, including the entire snap settlement. The default max-height must
remain released until WAAPI finishes; otherwise it clips the animated height and
autosize reads an animated scrollHeight as the resting content height. Settlement
cancels its fill before handing height ownership back to autosize. Typing in manual
modes performs no sizing measurements, and returning to auto explicitly permits
shrinking. Height preferences are local, not durable draft state.
While manual height owns the textarea, the autosize effect also drops text from its
dependencies instead of running and immediately returning on each edit. Returning
to auto reintroduces the latest text and measures once.
The composer keeps real textarea resizing while sheets use a translated frozen canvas.
Both share recent-velocity flick selection and an interruptible critically damped spring;
short flicks can change stops, while holding before release falls back to proximity.
The textarea's CSS minimum remains authoritative during downward resistance.

## Generated avatars

`AgentAvatar` uses local DiceBear Bottts Neutral artwork with rounded corners and
each identity's computed accent color as its background. Ordinary Agent faces use
trimmed, case-normalized Agent names. Subagent task faces use the child session ID
(tool part ID until assigned), consistently across task rows, activity headers,
and work status. `useAgentAvatarPalette` reads the current theme's resolved tokens,
so theme changes repaint the same face without render-time DOM probes.
Only the tiny message-header badge face passes `shape="square"`. Composer faces
are 20px on desktop/VS Code and 24px on mobile web (22pt in native iOS); other
surfaces retain their existing sizes.
Assistant consumers
explicitly pass `kind="assistant"` to select the procedural Open Mascot adapter.
`lib/generatedAvatar.ts` imports only the Bottts Neutral DiceBear definition;
Assistant SVGs come from the pinned MIT core in `lib/assistant-avatar/`.
Both styles use deterministic seeds and no remote avatar requests. Live Assistant
list/header/processing faces switch idle/thinking; history and native PNGs stay
static. The saved animation switch, system reduced motion, document visibility and
intersection gate the shared animation clock. See `../assistants/DOCUMENTATION.md#generated-avatars`.
Avatar frames lock min/max width and height and clip animated artwork.
Assistant IDs, ordinary Agent names, and subagent task IDs
are the respective seeds. Explicit emoji overrides remain supported. The memoized
component generates only on seed/style/emoji/palette changes, not draft or streaming
updates. SVG images isolate internal definition IDs and preserve attribution
metadata from their renderer.

Identical faces also share generated SVGs across row mounts through the existing
`DualLimitLru` (128 entries / 1 MiB of UTF-16 key + URI payload). Keys include
normalized identity, kind and resolved background color. Exported SVGs are static;
the live Assistant adapter animates paths independently of this cache.
Theme changes select another key; style definitions are build-pinned. Artwork is
pure local data, deliberately reusable across runtimes with the same inputs,
without retaining session/auth state. Oversized results are returned but not
cached. `generatedAvatar.test.ts` guards duplicate generation and variant/bound
semantics; per-component memoization still skips unrelated render work.

Native iOS composer receives an optional `agentIcon` PNG generated only when its
Agent identity or palette changes. Late rasterizations are fenced on identity/availability
changes; text echo does not resend the image. Old shells retain the identicon
payload fallback. Native Assistant share catalogs carry optional procedural `avatarPng`
data, generated serially; a newer publication cancels older work. Native share
UI and shortcut donations prefer the PNG, retaining emoji and legacy catalog
fallbacks. A new native build is required for PNG-consuming native surfaces.

## Image presentation

Native hit-only file-cache lookups are optional. If desktop IPC is unavailable (including a window-only remote-plugin document), complete-body and range reads fall back to the active runtime. Runtime authorization, cancellation, scope checks and source failures remain authoritative.

The complete-byte owner is `lib/runtime-file-resource.ts`, backed by `runtime-file-store.ts`; `runtime-image-cache.ts` and `runtime-image-store.ts` remain compatibility exports. Existing IndexedDB name/version and opaque content keys are preserved. Image display leases, file reads, saves, cached video ranges, descriptor attachments, imports and confirmed uploads share that owner. `readRuntimeFile` returns a leased Response: EOF awaits verified commit; cancellation releases only that reader. The 32 MiB limit controls retention, never whether a valid read/export is permitted. `readRuntimeFileBlob` supports legacy Blob/base64 destinations without adding a size rejection. Full-body retention uses 128 entries/256 MiB persistent and 32 entries/64 MiB/five minutes memory. Cold ranges and oversized bodies stream without entering the complete-body store. Partial coverage is never persisted as a complete file.

Video popup entrypoints capture `video.directory`; playback and save resolve relative paths against that origin snapshot. Direct video playback uses an authenticated browser URL for streaming/seek (this does not guarantee reuse of the client body store). The iOS range bridge reads through the shared owner, including raw API URL query/grant parameters, and releases on auth changes. Browser Relay playback/downloads and native export retain their previous Blob/base64 compatibility paths when no streaming destination exists. Those oversized bytes are uncached; their existing browser/device memory constraints remain. Direct oversized downloads use browser streaming. A cache budget must not silently narrow the supported file size.

File saves reuse complete source bytes, including relative `/api/fs/raw?path=...` URLs with directory/outside-grant parameters. Web/VS Code downloads and non-optional text reads use the owner; optional reads retain the existing missing-file contract. FilesView binary reads are selected inside the owner, while direct image/PDF/HTML navigation uses `directFileResource` with explicit browser-cache semantics and unchanged URLs. Mobile Relay HTML and local Mermaid reads share the body owner. External HTTP/CORS reads use `readFileResourceUrl` as uncached sources. Native share uses `importFileResource` to read staged bytes once and optionally seed bounded reuse; it is not a remote download. Prompt and Assistant attachment PUTs still execute and verify their real destination results before seeding; cache failure does not fail an already successful upload. Assistant protocol/upload limits remain distinct from cache capacity.

HTML direct previews retain original URLs/origins, relative references and existing iframe sandbox behavior. Host `/api/fs/serve` offers private ETag revalidation after authorization; this is independent of client persistence and is not guaranteed durable across browser restarts. Plain HTTP LAN HTML subresources remain browser-owned. No environment blocker or service worker is introduced.

Markdown (Markstream and marked) and attachment popup entrypoints capture the originating directory in `ToolPopupContent.image.directory`. The fullscreen gallery resolves relative sources against that snapshot, so changing the active session/worktree while it is open cannot reinterpret its paths. Callers without a snapshot retain the active-directory fallback.

`ToolOutputDialog` image and video previews share `MediaSaveButton`: one icon-only
download action in the shared control row, alongside image zoom controls. Mobile
uses the bottom-right safe area with 32px visible circles, 16px icons and preserved
36px hit areas. These compact flat circles have no borders or
shadows. Desktop uses the bottom-left with larger controls and icons, reusing the
close button's shared `mobileGlass` variant and design tokens. The gallery counter
has its own rounded backing matching the mobile circles, with opaque light text
so it remains readable over bright images; the toolbar row stays transparent.
Both use a filled
download icon. Video uses the same toolbar shell and control
sizing. The saving/check states replace the icon in place. Clicking materializes bytes and
saves directly; pending shows a dim circular track and a solid arc reflecting
downloaded byte percentage, success a checkmark. There
is no save sheet, long-press save, visible status text or success toast. Accessible
labels/live status remain localized. A failed save restores the retryable download
icon; native document-picker cancellation returns to idle. Browser success means
the download was handed off to the browser, not a confirmed filesystem write.
The control is keyed by source/runtime, rejects duplicate clicks, and aborts reads
on close or source change. Late native completions cannot update another preview.
Native picker/Photos confirmation remains owned by the OS. Thumbnail and Markdown
images open the full-screen preview; they no longer own save gestures or sheets.

`lib/download-progress.ts` reads response chunks and publishes only changed integer
percentages (at most 101 notifications per transfer). Image and video saves share
this reader, including native one-use image source re-reads. Host raw-file saves
request the full `Range: bytes=0-` so `Content-Range` supplies the total even when
Relay strips `Content-Length`. Cached Blobs are already downloaded and report 100%.
The full ring remains until native save completes; it does not imply Photos/file
write success. Unknown or compressed decoded lengths keep the faint track until
EOF rather than fabricating progress. Interrupted/truncated reads never show the
success check. The ring has an accessible percentage but no visible numeric text.

Video attachments and Markdown video-file links open the same overlay with a
native `video controls playsInline` player; there is no third-party player or
autoplay. The player shares the bottom download control with images.
HTTP/data/blob sources play directly. iOS shells with `YuriVideo` give the
native player an opaque loopback HTTP URL. Its Range reads pass through
`native-video.ts` → `runtimeFetch` → the existing direct/Relay transport, capped at
1 MiB per request. Seek/disconnect and preview/runtime teardown abort the request
and release the native lease. Host `/api/fs/raw` must support 206/Content-Range;
an old Host that ignores Range fails without downloading the entire file.
Other runtimes and older iOS shells retain an abortable, runtime-keyed query and a
temporary blob URL released on close (full download before playback).
Codec support follows the browser/WebView. Save reuses loaded bytes when available.
Web/Electron download the original file; Capacitor video save uses the existing
system document picker, while image save still writes Photos. VS Code local video
save uses `files.downloadFile`; nonlocal video save reports unsupported failure.

Native image display URLs are one-use streams, not reusable download URLs.
`relay-image-stream.readRelayImageDisplayBlob` retrieves the verified backing Blob
or reloads its canonical runtime path under the same transport identity. Backing
Blob references follow the existing display lease/TTL and 32 MiB per-image bound;
they are not a separate cache. Runtime-file saves fetch original bytes directly,
without opening another native display stream. Electron's reusable disk-asset
URLs retain their ordinary fetch path. Save never fetches the iOS video loopback
URL as a whole-file download; it uses the canonical source.

`message/mediaPreviewTransition` animates loaded image previews through one temporary,
fixed, paint-contained crop frame and one image. Thumbnail `object-fit`, percentage
`object-position`, clipping ancestors and matching-frame corner radius determine the
return geometry. Frame bounds and image translation/scale animate together in both
directions; no React state updates or DOM measurements occur per animation frame.
Completion and cancellation remove the temporary layer and restore image visibility.
Successful close retains the viewer's opacity-zero animation until overlay cleanup,
so deferred React unmount cannot briefly repaint the fullscreen image or backdrop.
Non-image previews retain View Transitions; unavailable geometry and reduced motion
retain the shared fallback. All `MediaPreviewOverlay` image consumers use this path.

Markdown content, attachment thumbnails/gallery, Assistant contact images and composer attachments use `LoadingImage` from shared UI on desktop and mobile, over direct or Relay connections. URL acquisition and browser decode are separate pending phases; both show the shared dotted shimmer canvas. Body images use one fixed-height frame (`contentFrame`, 10rem) in every phase so late image bytes never shift the transcript: 320px wide on desktop, full message width on mobile, with the image contained inside and full size available in the preview. Thumbnail slots retain their existing square size. Fullscreen previews and file sheets use `ImageLoadingPlaceholder` during resource acquisition. Failures end loading and preserve the owning surface's error/retry path; image preview/save metadata continues to carry the original source. Legacy Markdown keeps its DOM presentation owner and only marks streamed images loaded after the actual image load event. See `../ui/DOCUMENTATION.md#image-loading`.

## Mobile automatic read-aloud

Read-aloud content defaults to `final` (existing explicit choices are retained).
This mode selects the exact trailing body part owned by sorted presentation,
using `getSortedBodyPartIndex` from `assistantMessageLifecycle.ts` in both
`projectTurnActivity` and MessageBody. Only the last assistant of a settled,
non-compaction turn can supply this text. It is the full body part, not the last
paragraph, a heading heuristic, or a generated summary. Live and sorted views,
manual read-aloud and automatic read-aloud use the same choice; intermediate
Activity actions have no speech target in this mode. Other content modes retain
their existing behavior. Settings uses a Select with a description per option.

The chat overflow menu owns a device-local persistent auto-read preference through
`mobile/chat/MobileAutoRead.tsx`, stored as a boolean at `yuri.auto-read`
using `useLocalStorage`. Missing/invalid values default to off. Navigation,
runtime switches, unmounts and playback failures stop transient playback without
clearing the preference. Explicit menu/message stop actions persist off. Restored
sessions unlock browser audio on their next user pointer gesture.
Each active, hydrated session snapshots completed message IDs and the
current creation watermark only after transcript hydration. Assistant bodies
notify `auto-read-context.ts` after completion, streaming cooldown and two paint
frames. Historical rows, duplicate mounts and other sessions cannot requeue a
reply; a reply observed live can complete even before the snapshot watermark.
Only assistant text is read, not reasoning or tool output. Audio is serialized
using actual playback completion callbacks, not synthesis-request completion.
The separate auto-read playback context exposes the active session/message identity
to message actions, so the matching read-aloud button shows its active state and
can stop automatic reading. Completion, cancellation and backgrounding clear it;
playback updates do not invalidate the rendered-reply registration context.

The provider keeps high-frequency transcript subscriptions outside MobileApp;
context identity stays stable across token updates. Disable, navigation and
runtime changes stop speech and clear the queue. Backgrounding stops playback
and releases the screen lock; foregrounding reacquires while still enabled.
`useMessageTTS` shares voice settings, unlocks mobile audio on the menu gesture,
and fences late summaries/playback callbacks after cancellation. Message read-aloud
has one active owner per UI instance, shared by manual and automatic reading across
sessions. A new request stops the previous owner before preparing its text; unmounting
the owning message stops playback, while removing an inactive message cannot cancel
the new owner. Native mobile
uses `YuriScreenAwake`; browsers use Screen Wake Lock and show a localized
warning when unavailable. Native support requires a new iOS/Android binary.

## Mobile hold-to-talk

Desktop dictation writes provisional transcripts directly into the existing
composer via `useDictation.onPartialTranscript`. ChatInput captures the starting
document text and replaces its own successive preview, so a final correction
does not append a duplicate transcript. Programmatic edits retain composer reference
handling. If the user changes the preview, subsequent ASR results relinquish
ownership rather than overwrite that edit. Escape stops recognition and clears
preview ownership and highlighting without changing the current input text.
After failure, clicking the desktop microphone discards the failed audio, retains
the current text and starts a fresh capture; it never silently replays the old audio.
Desktop provisional speech uses the existing composer highlight overlay with an
underline only over the appended transcript (excluding the original draft and
separator). Finalization clears the decoration even when the text is unchanged.
The decoration is scoped to the draft identity and exact preview text; switching
drafts or editing the text cannot underline unrelated content.

When dictation is enabled and microphone capture is supported, `ChatInput` mounts
the mobile speech controls. With voice input disabled, no mobile dictation engine
is mounted: normal placeholders, native selection and input behavior are restored.
The legacy dictation toggle listener also requires the enabled/supported gates.
When enabled, it mounts
`HoldToTalkComposer` keyed by DraftKey. The existing expanded card, compact pill,
attachments and footer remain visible and unchanged; only the empty input's
placeholder changes. A short tap focuses the existing textarea. Holding an empty,
input for 300 ms records, whether or not it already has focus. Empty input touch
ownership (`touch-action`, selection/callout suppression) is also focus-independent;
native selection/context menus are blocked on the empty textarea and compact
placeholder even before/after a hold. Toolbar controls are excluded. The empty
state attribute scopes CSS so nonempty inputs regain native behavior. The 300 ms
timer rechecks emptiness/editability before starting capture, including paste or
keyboard input during the pending hold.
An explicit non-passive `touchstart` listener prevents native touch selection on
eligible empty input surfaces; a confirmed hold blurs the textarea to dismiss its
native caret. Short taps still focus it, and nonempty drafts keep native editing.
Horizontal displacement of 64 CSS pixels
selects cancel (left) or send (right); entering the bottom targets selects the
half under the finger regardless of displacement. Release in the center focuses the
existing textarea for editing without sending. Release on the right sends the final text
through the same primary send action as the Send button, preserving queue admission,
establishing-session follow-ups and submission-flight guards. Both releases hide the
gesture targets and keep the overlay in B2 loading until microphone teardown and
recognition finalization complete. Background blur cannot cancel this finalization.
Edit release restores textarea focus after loading ends. The last partial text is
staged in the composer and replaced by the final text; user edits take precedence
over late results and suppress automatic sending. Processing stays in the composer
hint, with no post-release cancel action. Late errors use a toast and retain the
staged text; completion dismisses the loading overlay. Returning
to the center outside the targets restores edit. Pointer interruption/backgrounding cancels; leaving the draft fences
late recognition results. Nonempty inputs retain native text selection/editing;
disabled and read-only inputs cannot start capture.

The recording leaf portals a pointer-transparent overlay to the document body,
outside composer transforms, with a scrim covering the bottom as well. The original top gradient, six volume-responsive
animated lights and safe-area-positioned underlined captions remain intact.
The bottom gesture stage scales with viewport width (400×226 SVG plus safe area).
Cancel and edit occupy mirrored halves as concentric annular segments with rounded
inner ends and a center gap. Their 600/524 radii and the lower surface's 500 radius
share the same (200, 620) center; one SVG preserves that geometry at every width.
The muted translucent fills and light labels sit above an opaque curved holding
surface; the underlying composer must not show through that lower surface.
There is no command action. Active targets increase their background opacity
from 12% to 40% for a brighter highlight; text opacity and scale stay unchanged.
The original input placeholder also shows release-to-send, cancel,
edit, or processing. The underlying input surface becomes transparent during the
gesture without changing layout or pointer capture. Only these low-frequency transitions reach
ChatInput; captions and volume remain leaf-owned. Partial ASR
text is underlined until finalization (the current transport supplies provisional
full text, not per-word stability). Reduced-motion preferences disable animation.
While holding, errors replace the listening caption
with red alert text and make the entire overlay dismissible by a tap. Releasing
an ongoing hold after an error cancels instead of confirming; idle startup errors
are discarded as well as failed recordings. The holding finger stays tracked
within a global pointer lifecycle after starting on the original composer.
Move/up/cancel listeners run on window capture and filter by the initiating
pointer ID. Leaving the textarea or losing element pointer capture does not
cancel; actual pointercancel, backgrounding, or draft disposal does. The gesture
does not depend on textarea pointer capture surviving layout/keyboard changes.
The hold-to-talk leaf renders no additional idle chrome. With ASR enabled and
capture supported, both compact and expanded mobile footers also expose a
microphone button. Both control one `DesktopDictationButton` leaf in mobile
interaction mode: provisional text is inserted and underlined inline using the
same preview ownership as desktop, without a recording overlay. Only another
microphone click finalizes; touching elsewhere, scrolling, button/window blur,
visibility changes and keyboard shortcuts do not finalize or cancel mobile capture.
Its active lifecycle disables hold-to-talk so the two entry points cannot capture
simultaneously. The click-to-record leaf is keyed by DraftKey and uses stable props
at its memo boundary. Draft/runtime disposal still releases capture and fences late
results; capture errors retain their existing recovery behavior.

Captions and volume updates are owned by the leaf, not ChatInput or a
global store. ASR-enabled mobile uses the web input surface, including Capacitor
iOS; the native composer overlay is disabled while this feature is enabled.
Volcengine uses live streaming captions; other providers retain their existing
partial-result cadence. See `packages/web/server/lib/dictation/DOCUMENTATION.md`.

Composer horizontal session-switch gestures and their preview/transition UI have
been removed. The transcript's session-list gesture still excludes the complete
`.yuri-mobile-composer` so it cannot compete with dictation or text editing.

## Markdown math delimiters

Markstream's `customMarkdownIt` adapter replaces its permissive inline math rule with the shared `markdownMath.matchDollarMath` pairing used by the legacy renderer. Dollar currency in prose must remain literal in both streaming and completed messages. Explicit `$...$`, `$$...$$`, and `\(...\)` inline formulas remain supported; incomplete inline formulas stay literal until their closing delimiter arrives. Block math remains owned by Markstream's block rules. Code spans and escaped dollar signs follow the normal Markdown tokenizer. An inline candidate never crosses an inline code span (a currency amount must not pair with the `$` of a `` `${template}` `` inside backticks), and a candidate whose body contains CJK characters or CJK/fullwidth punctuation is prose, not TeX — Chinese amounts are often glued to surrounding text without spaces. Digit-leading candidates with spaces or quotes in the body are likewise prose even when they contain `/` or `+`; spaceless digit-leading formulas (`$2\pi$`, `$1+x$`) still pair. Coverage: `MarkstreamRenderer.codeblock.regression.test.tsx` and `markdown/markdownMath.test.ts`.

## Mermaid diagrams

`markdown/mermaidRender.ts` owns synchronous Pele SVG rendering for both Markdown paths, tool previews and fullscreen diagrams across all runtimes. There is no ASCII mode or renderer selector. UI-store v14 drops the obsolete `mermaidRenderingMode`; host/client settings sanitizers ignore old values.

The renderer retains a 100-entry / 8 MiB LRU keyed by resolved theme colors, local date (Gantt today markers), and source. It sanitizes Pele output, disables diagram links and external images, and embeds theme variables on the SVG so downloads retain their colors. Pele's source/output/edge limits remain enabled. Invalid or incomplete source stays visible as escaped source and is retried when the source changes.

Use `render()`, not `mount()`: `mermaidViewer.ts` remains the sole pan/zoom/resize owner. Layout is independent of container width and automatic direction switching is disabled, keeping cache geometry stable across inline/fullscreen and mobile views. `decorate.ts` scopes accessibility IDs per displayed instance, while the original SVG is retained for unzoomed downloads. Coverage: `mermaidRender.test.ts`, `mermaidViewer.test.ts`, and `useUIStore.mermaidMigration.test.ts`.

`ToolOutputDialog` uses `MediaPreviewOverlay` for both images and Mermaid: one portal, focus boundary, close control, mobile Back route and shared-element transition lifecycle. Mobile previews fill the viewport with an opaque black canvas; desktop previews fit within 80% viewport width / 95% height, with a 70%-opaque black backdrop for images and 90% for Mermaid. The existing image and Mermaid viewers retain their own pan/zoom. Mermaid previews pass the selected dark theme (default dark fallback) through `SimpleMarkdownRenderer.mermaidTheme` to Pele, including node, edge, text and accent colors. Inline diagrams retain the page theme; exported preview SVGs carry the preview's dark colors.

Activation passes the actual clicked DOM element as ephemeral `ToolPopupContent.previewSource` (never persisted). `mediaPreviewTransition` hands a unique snapshot name from that source to the preview and back using the browser View Transitions API, with a 280ms transition and cleanup on interruption/unmount. Missing/offscreen sources, unsupported browsers and a changed gallery image fall back to a 150ms fade; reduced-motion skips animation. The preview never scans the transcript for a matching URL. Mobile system/gesture/history Back dismisses the preview before the underlying page; image pointer-dismissal guards never block explicit Back. Coverage: `ToolOutputDialog.preview.test.tsx`, `mediaPreviewTransition.test.ts`.

Both preview kinds keep the canvas edge-to-edge and toolbar spacing fixed. Only the mobile close button respects the top and right safe-area insets, with its normal spacing added inside the safe area.

## Composer closed-picker work

Project and branch picker catalogs are rendered by leaf components inside the existing popup/sheet presence boundary (`DraftProjectItems`, `BranchList`, `WorktreeItems`). Composer typing must not filter or construct closed project/branch rows in the parent render: hiding a portal does not defer evaluation of inline JSX array maps. The popup remains mounted through its normal exit lifecycle, so list content survives closing animations without an extra presence flag or cache. `composerClosedPickers.test.tsx` covers repeated closed renders, first opening, selection and closing again with 300-entry catalogs on desktop and mobile presentations.

ChatInput reserves the initially measured input/chrome height plus the current Changes / TODO / queue accessory height. Only the accessory region is observed for subsequent occupancy changes. Typing, wrapping, height-handle dragging and spring settling never update the root reservation; publishing inherited root inset variables on those frames would restyle the entire transcript. The base measurement resets when the web occupancy publisher is disabled or unmounted.

## Composer pointer focus boundary

`composerFocus.preventComposerActionPointerFocus` owns the mobile form's capture policy. Toolbar actions inside the actual composer DOM prevent default focus and mark the composer gesture; the textarea and attachment controls retain their existing exceptions. React portal events still traverse the parent form, so the handler must check `currentTarget.contains(target)` before applying this policy. Model/agent pickers and other portaled dialogs own their inputs independently: do not cancel their pointerdown or compensate with manual pointerup focus. `MobileWindowMotion.focus.test.tsx` exercises this production handler with the real portaled picker, including toolbar prevention and search permission.

## Clipboard images

ChatInput prioritizes image bytes from clipboard files/items over accompanying file paths (including clipboard-manager and Electron native paths). Path-only plain text accompanying an image is omitted; accompanying prose is retained. Files take precedence over item representations, with a single preferred PNG/WebP/JPEG/GIF item when macOS exposes format twins. Without image bytes, existing file-reference paste behavior applies; no local path is fetched from a potentially remote runtime. Coverage: `ChatInput.paste.test.ts` executes the production paste callback with controlled clipboard payloads.

## Prompt navigator

`MessageListEntry` owns the Markdown hydration provider inside its existing memo
boundary. Both history renderers pass the primitive `hydrateMarkdown` prop;
virtual-range/scroll updates with unchanged entry props execute neither the row
nor its provider. Hydration-window policy still owns placeholder release, and a
boolean change reaches the existing mounted content without replacing row DOM.
`MessageList.hydrationBoundary.test.tsx` covers 50 unchanged parent updates,
placeholder release, DOM continuity and fresh callbacks; restoring the outer
provider placement fails the render-count guard.

On direct-connected PC surfaces with fewer than 12 authored-user turns loaded, `useDesktopHistoryWarmup` requests one 50-message history page after content readiness and 800ms of unchanged messages, scroll height and position. Relay disables this idle warmup on every surface; the callback rechecks the transport before requesting a page, including transport changes without a render. Explicit history loading and correctness recovery remain available. The enlarged page commits together rather than cascading small pages. The 50-message cap bounds tool-heavy sessions; it does not guarantee 12 turns when a turn contains many messages. Mobile, inactive/hidden views, initial hydration, working sessions and concurrent history loads do not warm. A failed or short page does not automatically retry during that visit; explicit pagination remains available. Existing timeline prepend compensation owns the viewport; warmup does not release follow, show a loading indicator or toast. Only eligible views sample geometry, at 200ms intervals; starting the single request stops sampling.

`StaticHistoryList` retains the same root/row-parent structure when history crosses the virtualization threshold. Every acquisition authorizes and resolves its file through the existing stat Query with `fingerprint: true`. The Host/VS Code returns SHA-256 of actual content, not a hash of path/size/mtime. Clients compare downloaded bytes to that SHA-256 before committing. This still relies on truthful filesystem version metadata; filesystems that fail to update ctime on external changes cannot provide that guarantee.

The history frame is a `minHeight: totalSize` box with padding for the unrendered range (`resolveTanstackHistoryFrameStyle`), not `height: totalSize`: visible rows live in normal flow so sticky headers work, and the live tail is the next sibling — a cached-short row must grow that frame and push the tail down instead of overflowing onto it. Core 3.19 can report negative row starts while holding an unwritable scroll correction; a negative inner margin inside a flow-root preserves this shift without transforms or margin collapse. `scrollToFn` writes `scrollTop` and that minHeight **synchronously** (`applyTanstackHistoryFrameMinHeight`) — deferring to a microtask/rAF desyncs core's end-anchor offset from the DOM and blanks cold session open; writing `height` would re-lock the overflow. Session open pin in `ChatContainer` waits until the transcript gate leaves `hydrating` and re-pins once when message count first goes `0 → N` for that session so deep links do not pin against an empty skeleton.

`useChatAutoFollow` owns following/released policy and composer/content observers, but delegates virtualized bottom writes through `MessageListHandle.scrollToBottom`. The handle returns whether an active list handled the request; normal-flow transcripts retain the DOM fallback. Passive growth uses `reveal: false`; explicit jumps re-arm Markdown reveal. Resume invokes only `goToBottom`, which updates policy and makes one list request. TanStack does not run the outer overflow-toggle/24-frame force-bottom watchdog. User release cancels the core scroll command; virtualizer-threshold anchor restoration also goes through `scrollToOffset`. `ChatHistoryScroll.chrome.test.ts` covers cold entry, prepend/late measurement, jump-to-latest, external live-tail growth, and released reading after growth. iOS gesture checks use its optional native fixture.

`markdownHeightCache.ts` records the height each content string actually rendered at, and the deferred placeholder in `MarkdownRenderer` reserves that box instead of laying out the Markdown source as an invisible spacer. Rendered Markdown is far shorter than its source — fenced code, link targets and table pipes all collapse — so the plain-text fallback overshoots and the swap into real content shrinks the row, which the virtualizer then compensates by yanking the scroll offset. Heights come from `ResizeObserver` entries rather than a measured read, keeping a batch of rows revealing together from thrashing layout, and are recorded only for a settled non-streaming render. Only the rich renderer records and reserves; the simple renderer produces different output for the same source. Every entry is dropped when the column is next measured at a new width, because one width applies to the whole transcript.

Marked parse (segment / heal / KaTeX) runs in the same Shiki worker as highlight (`parse` job). The main thread sanitizes with DOMPurify and patches via morphdom. Short fence-free text stays on the sync main-thread fast path. A worker failure falls back to the main parser so a bubble is never blanked. Streaming sends only uncached tail blocks. Every entry point into the Shiki worker — `highlightCodeInWorker`, `highlightLinesInWorker`, `highlightTokensInWorker`, `parseMarkdownInWorker` — is memoized in `markdownHighlightCache.ts` (`HighlightMemo` constructed in `markdown-worker.ts`) and owns that caching for all callers, including the file and diff surfaces. Keys are content-addressed (language, plus theme name for token runs, plus the code itself) rather than derived from a message or block position, because `markdownCore`'s per-block cache is keyed by part id and block index and therefore misses whenever a message re-segments or history scrolls far enough to evict it. Concurrent requests for the same snippet share one worker job, and the job is cancelled only once every caller has abandoned it, so a row scrolling out of view cannot strip highlighting from a row still waiting on the same code. Failed highlighting resolves to `null` and is never cached, keeping a worker outage retryable.

Open/streaming fences stay off the full `codeToHtml` path until they close. The parse stamps `data-md-stream-fence` on that last `<pre>`; morphdom preserves its highlighted children (`shouldPreserveStreamingFence`) and `highlightLinesInWorker` tokenizes the latest source. `applyPrefixDiffHtmlLines` reuses unchanged leading line spans and only replaces/appends/truncates the suffix (`codeStreamHighlight.ts`). A worker miss advances the latest source as escaped plain text while retaining already highlighted equal prefix lines; failure stays retryable, and stale worker completions cannot overwrite a newer source. Line spans retain literal newline separators so highlighting preserves source text and preformatted height. Closed fences keep the existing full-highlight splice.

A fence whose info string is a `startLine:endLine:filepath` code reference is split by `codeFenceInfo.ts` into the Shiki language id to tokenize with — resolved from the referenced file's name or extension — and the label shown on the code card header. The two cannot be the same string: the id has to be lowercased to match Shiki's registry, and the whole triple matches no grammar at all, so treating it as a language leaves every reference block uncolored under a mangled path. The highlight pass stamps `data-md-label` alongside `data-md-lang` only for references, so plain fences still morph to the markup they had before; `decorate.ts` prefers that label and otherwise parses the `language-*` class marked emits, which is all the synchronous first paint has. A bare `mermaid` fence stays unhighlighted for the diagram pass, but a reference to a `.mmd` file is source and colors like any other.

`ToolOutputDialog` owns image gallery selection and the image-only full-viewport viewer. File image previews (`FilesView`, `MobileFilesSurface` / `MobileFileDetail`) open this same viewer on click so pinch/pan/wheel/zoom controls stay one implementation. Keyed `ImageViewerSlide` children own Relay-resolved image leases, decode state, and fitted dimensions. Mobile mounts at most the current image and its two unique neighbors; promotion retains the neighbor's decoded element and lease. A two-image gallery repositions one neighbor for either swipe direction rather than duplicating a one-use native stream. Every gallery change resets the image to its fitted `1x` transform.

`imageViewerTransform.ts` owns scale-origin, pinch-midpoint, pan, boundary-clamp math, direction locking, overflow handoff, and release classification. Mobile horizontal dragging moves the gallery continuously; downward dragging translates/shrinks the image and fades the independent `MediaPreviewOverlay` backdrop and controls. Above `1x`, image pan consumes movement first; only overflow beyond the image bounds plus a 32px handoff threshold can drive gallery or downward-dismiss motion. At `1x`, a gesture locks its axis after movement exceeds tap tolerance; downward diagonals (vertical travel at least 0.6× horizontal) and every single-image drag lock to pull-to-dismiss so it never stalls on an undecided axis. Above `1x`, the first edge pushed past its handoff threshold locks the axis. Release uses overflow distance and the 100ms sample-window velocity to commit or rebound, not total movement through a zoomed image. Gallery track and dismiss offsets are Motion values; release settles them with a critically damped spring seeded with finger velocity toward the target, and gallery selection commits when the spring finishes. A new touch stops the spring and catches the track or dismissal at its current offset instead of being ignored; zoom controls and other input stop it without committing. On mobile the canvas and active image are `touch-none`, and the canvas also cancels `touchmove` through a non-passive listener: Android Chromium resolves touch-action on the compositor against transformed (zoomed) layers and can otherwise start a native pan that `pointercancel`s the drag, which only rebounds. Cancellation rebounds, resize cancels transient motion while reconciling zoom bounds, and unmount cancels pending frames/animations. Reduced-motion skips automatic settling animations. Opening transitions are cancelled on pointer down so they cannot hide a manipulated image; closing transitions reject new pointer gestures. Downward close flushes its final frame before the existing return-to-thumbnail animation measures the target.

Pointer, wheel and spring updates remain ref-owned and coalesce into one Motion `frame.render` step with no React state/resource work per move; unchanged style values are not rewritten, independently of gallery length. The interaction budget is one bounded visual write per display frame (16.7ms at 60Hz, 8.3ms at 120Hz); image fetch/decode is outside the pointer path and retained only for the three mounted slides. `ToolOutputDialog.preview.test.tsx` checks a 1000-item gallery with 100 pointer events, slide identity promotion, pan-to-overflow handoff, cancellation, resize, and animation lifecycle. These operation-count tests do not prove native-device frame rates.

On mobile, a stationary single tap closes at every scale after the 280ms double-tap window, and pinch zooms. A second stationary tap within that window and 32px zooms to `2x` around the tapped point (clamped to image bounds), or restores `1x` when already zoomed, without closing. A mobile close arms a short, coordinate-scoped native capture guard before closing, consuming the browser's synthesized trailing click so the source image stays closed. Pinch, drag, gallery swipe, and cancelled pointers suppress tap close; continuing on one finger after a pinch can pan but cannot dismiss or navigate until a new gesture. On desktop, an empty-canvas click closes the viewer, while image, gallery, and zoom controls retain interaction ownership. Escape closes on every hardware-keyboard surface. The localized close action receives initial focus, the viewer traps focus, and close restores the previously focused element. Desktop double-click, wheel, drag, keyboard shortcuts, resize reconciliation, and the zoom controls share the same `1x` through `5x` clamped transform.

`MessageFilesDisplay` gates Relay image auto-load by known byte size (`imageSource.ts` `RELAY_IMAGE_AUTO_LOAD_MAX_BYTES`, 1 MiB; `imageRequiresManualLoadOverRelay`). A slim oversized image defers whole-message visibility materialization and a file-stream (`file://`/host-path) oversized image defers its own byte fetch until the user taps that image's load row. Each gated image is its own compact clickable row (icon + filename + size). Tapping one approves only that image; slim fills still use one `session.message` request, but unclicked siblings stay gated until tapped. `data:`/`blob:`/`http(s)` URLs and unknown sizes never gate, and direct (non-Relay) transports keep unconditional auto-load. After a user send, the legend timeline enters `anchoring-new-turn`. `beginOptimisticSend` marks the pending send **before** it inserts the optimistic user row, so MessageList's render-phase consume sees the pending count on that same insert (ChatInput paints the row well before `sendMessage` runs). Pending is the send signal: consume parks the current last user row even if a sibling or earlier paint already recorded that id. MessageList passes that live `nextAnchorId` into the list on the same render — waiting on `useState` lets end maintenance pin the just-sent row to the bottom for a frame. The consumed id is remembered at module scope (`userSendAnimation`) so a React Strict Mode remount — fresh component state, pending count already zero — can re-latch the same send instead of treating the transcript as a session swap. That latch is not last-read memory: the primary list delayed-clears it on leave (`queueMicrotask` after layout unmount) so a same-turn remount can still peek and a later reopen cannot park on the old user row instead of `initialScrollAtEnd`. Idle renders and secondary transcripts (context panel `enableSendPark={false}`) must not consume or clear that remount latch. Occupancy is a trailing list item after that last turn (`resolveReplyReserveUpdate`: leftover of the chrome-aware middle window, capped at 40% of the list viewport, `getFixedItemSize` so the virtualizer can park immediately), not a `minHeight` on the turn and not a footer — collapse, hydration, and streaming keep writing the row's natural height through `resolveShrunkItemSizeUpdate`. On immersive mobile the list is the full screen, so usable height subtracts the measured header (safe area + floating nav) and footer (composer inset + tail); the parked row sits just below that header. There is exactly one bottom inset in that math — the measured footer. `TimelineList` previously also took a `composerOverlayHeight` prop that `resolveUsableViewportHeight` and `getAnchoredTurnMetrics` subtracted on top of the footer; every caller passed `0`, so it was a second name for the same quantity and an invitation to double-count it. `endInsetHeight` is now the only one. The hole is the live edge — there is no further downward scroll room under it. Distance, the scroll-to-bottom pill, and `--yuri-native-composer-dock` all read that parked offset (`data-yuri-timeline-park-end`), not `scrollHeight`. **That published offset is bounded by the scroll room that actually exists** (`resolveParkedLiveEdgeOffset` with `resolveMaxScrollOffset`). Because the hole is capped at 40% of the viewport, it is routinely smaller than the window the anchor offset asks for: on a phone (viewport 852, header 135, footer 290 ⇒ usable 427, cap 341) the scroller stops 86px short of the ideal offset right after a send and 46px short a few tokens later, closing only once the reply is ~120px tall. Publishing the ideal there let the platform silently clamp the park scroll and then reported the resting viewport as 86px from its own live edge — past both the 40px re-arm band and the 80px pill threshold — so the scroll-to-bottom control appeared at rest and the at-end re-arm was withheld until the reply grew, then both flipped. The one-shot park *scroll* deliberately still targets the unbounded ideal, since the scroller clamps a too-far target itself while a content length that has not counted the fresh hole yet would park short and stay there. **Nothing corrects the position toward the parked edge on scroll.** The hole makes that offset the end of the content, so the scroller's own bounds hold it and a touch surface keeps its native rubber-band; a per-frame correction read iOS overscroll `scrollTop` (which passes the maximum mid-bounce) as "scrolled past the edge" and wrote scroll under a live gesture, felt as the transcript fighting the finger. Slack below the edge only opens as the reserve is being dropped, which returns to `following-end` regardless. Live status (`StatusRow` / 正在发送消息 / 思考中) stays inside the newest turn row so the reserve cannot push it to the bottom; the legend footer keeps only questions, permissions, and the composer inset. The working hint uses the same last-assistant `hasConfirmedFinalBody` settle as Changes chrome and unmounts in that commit (no 600ms step-gap linger), so it cannot flash after the turn is already done. The spacer starts as that capped hole and shrinks as the turn grows; a same-row collapse that would reopen it or overflow (`isReplyReserveOverflowing`) drops the reserve, clears the remount latch, and returns to `following-end`. Jump-to-latest returns to the parked offset and keeps the hole. A taller usable viewport (keyboard dismiss) keeps filling the hole up to the cap instead of dropping the park; an unmeasured (`0`) viewport must not wipe an already-seeded reserve. The list parks the row `CHAT_LIST_ANCHOR_OFFSET` from the top once per send (`reserveId` is the user-message id, so an ungrouped `msg:` row becoming a `turn:` relatches the spacer instead of treating that as a collapse). Composer send re-arms follow so a send from mid-history still parks. The TanStack fallback still force-pins to the bottom on send.
