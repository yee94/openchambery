Slash-command autocomplete auto-submit is name-whitelisted in `commandSelection.ts` (`AUTO_SUBMIT_SLASH_COMMANDS`: `new`, `fork`, `compact`, `undo`, `redo`, `model`, `goal`). Enter/tap on that short list runs the local action immediately (`/model` opens the model selector; `/goal` only arms). Everything else — custom/opencode commands such as `/loop`, magic prompts, `/timeline`, `/init`, skills — only inserts into the composer so the user can keep typing or confirm with a second Enter. `/goal` is arm-only: it flips goal mode, strips the slash token, leaves any trailing objective draft in the composer, and never auto-sends. Non-built-in OpenCode commands (including when `isBuiltIn` is omitted) share one durable reserved-slot chip insert (`composerTriggerIconDisplay`); plain fallbacks and hand-typed complete slash tokens are promoted to the same `/\u2003name` metrics in `typedSlashChipPromotion.ts` so icon spacing matches. Autocomplete query parsing strips that slot so ranking still keys off the bare name. `ComposerTriggerIconMark` paints reserved chips with equal insets and must not use `overflow-hidden` on the trigger span (that rewrites the inline-block baseline and lifts the icon above the label).

Current best-effort policy: direct submit and legacy queue admission use captured attachment views immediately. Attachment clear, failed-send restore, and queue cleanup results stay outside the send/admission gate. Sent chips clear from memory while persistence continues in the background; restoration errors are allowed.

A user abort (Stop / Esc / session-list stop / goal pause) synchronously marks the waiting queue head through `promoteQueueHeadOnAbort` before `session.abort`: the chip stays visible in the same "Sending…" presentation as a manual jump, and the follow-up does **not** paint onto the transcript until OpenCode actually consumes it (`sending`/`reconciling` or an authoritative user row). The worker still waits for `available + idle + settled`. Abort failure, a failed/unresolved head, or a completed dispatch that used another message ID rolls the presentation back so Edit/Send return. Question-dismiss abort on the send path does not promote. An aborted assistant paints short muted gray copy (`chat.messageBody.aborted` via `resolveAssistantErrorPresentation`), not the info alert chip reserved for SessionRetry.

Queue actions use server admission after authoritative active or paused ownership for the current transport, including a lagging `probing` cutover publication. Shadow, blocked, wrong-transport, and otherwise unconfirmed ownership keep queue mutations frozen; a busy Composer submit falls back to captured-session `steer` so the running turn remains interactive. Submission identity gates still disable unsafe targeting. An in-flight queue admission is visible and permits later send, admission, edit, remove, manual promotion, and reorder actions. Composer `submissionFlightKind='queue'` keeps the floating queue control visible with a queuing spinner (`queuingMessageAria`) after the body clears so admission still feels immediate. Pending-admission chips show spinner plus `chat.queuedMessage.queuing` text until the authoritative row replaces them. Manual send / jump chips keep the waiting row visible with spinner plus `chat.queuedMessage.sending` while a pending mutation, committed-ack send shadow, authoritative `manualDispatchRequested`, or an abort-promoted queue head is active; they hide only after authoritative `sending`/`reconciling` (or removal/confirm). Legacy dispatch rows (`sending`/`reconciling`) stay visible in the same "Sending…" presentation while optimistic on-screen dispatch is unconfirmed—message-on-screen optimism and chip Edit/Send lock are separate concerns. Client send-pending presentation times out after 8s and restores Edit/Send (legacy Send remains status-gated). After server admission commits, body consumption compares the captured Composer document with the current live document rather than DraftRecord object identity or persistence timing; identical delayed hydration cannot restore an admitted body, while any continued authored edit changes the document fingerprint and remains in the Composer. Attachments and inline drafts retain their independent occurrence/fingerprint checks.

Hosted mode skips the primary session-view cache, injects session/directory/composer surface/`SessionSurfaceContext`, merges `onRevertMessage` into that surface so message actions and the timeline restore into the host draft partition, and disables primary-only draft/prompt-navigator/return-to-parent features unless explicitly re-enabled.

A primary staged message edit is visible on its own row before send: `ChatMessage` reads `stagedMessageEdit` / `messageEditCommitting` from the session UI store and `MessageBody` replaces that user row's action group — keeping the row geometry — with a highlighted `editStaged` label plus a cancel affordance, then with a shimmering `editing` label once the commit is in flight. Staging is disarmed by the row's cancel affordance, by leaving the session, and by the Composer losing focus. A disarmed edit makes the next send an ordinary message that deletes nothing. Staging focuses the Composer textarea once per staged row (retried on the next frame when the node is not yet mounted or still disabled) so the restored text can be edited without a second tap. The paint is released by the commit, by the settle of the send promise, and by the non-handoff `finally`, and `endMessageEditCommit` only clears a matching session/message pair, so the redundant releases are safe. Hosted Assistant history uses the Assistant HTTP infinite query instead of per-session sync materialization. Its key and request closure capture transport identity plus runtime generation, and validate currentness before and after every page request. `lib/scroll/chatTailSpacer.ts` owns the empty tail under the newest message **and** the at-bottom band that reads it, because a spacer that outgrows its band strands the scroll-to-bottom pill on screen at rest. The tail is not `--oc-chat-foot-inset`: the inset reserves the chrome the Composer occupies (input, queued messages, changes / tasks strip) and the tail is the scrollable breathing room stacked on top of it, so the last message never ends exactly where that chrome begins. Desktop uses `10vh`; mobile uses a fixed 80px rather than a viewport fraction, because the visual viewport moves with the keyboard and browser chrome and a breathing tail would shift the at-bottom band under the reader. Mobile was previously 40px — sized like a scroll threshold rather than like empty space — which left a streaming reply pressed against the queue card with nothing to scroll up into. The two timeline engines consume it differently: `useChatAutoFollow` gets the chrome reservation from `.chat-scroll-foot-inset` padding and renders the tail alone, while the legend timeline derives content size from measured slots plus *style-object* padding and cannot see that class at all, so its footer spacer is `CHAT_TAIL_SPACER_MOBILE_WITH_FOOT_INSET_HEIGHT` (tail + inset) or its scroll math (`isAtEnd`, end maintenance) would ignore the reservation entirely.

This transition-local correction runs at most once and keeps TanStack core as the owner of ordinary virtualized prepend and measurement compensation.
