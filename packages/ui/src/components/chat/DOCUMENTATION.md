# Chat components

## OpenCode response status presentation

`message/assistantErrorPresentation.ts` maps the OpenCode V2 structured session errors from core `session/to-session-error.ts`, `runner/step.ts`, `execution/restart.ts`, and `compaction.ts`. It covers all twelve current `provider.*` types (rate-limit, auth, quota, content-filter, transport, internal, invalid-output, invalid-request, unsupported-operation, no-route, unknown, timeout), permission rejection, tool execution, compaction failure/unavailability/interruption and aborted execution. The protocol permits future type strings: unknown errors keep a localized generic failure label plus the upstream message, type and valid HTTP status. Structured types take precedence over legacy text-based auth detection. Labels are translated in every shipped locale; arbitrary upstream diagnostics remain verbatim.

`ResponseStatusRow` is the shared borderless, wrapping meta row for inline assistant failures, pre-assistant session failures and compaction failures. Failure uses alert semantics; recovery/retry information and interruptions use status semantics. All icons inherit the row's neutral muted foreground without variant-specific colors. Auth/permission use lock, timeout uses time, user stop uses stop-circle, generic interruption uses pause-circle, retry uses refresh, and restart continuation uses restart. `aborted` alone never claims a user stop: only the explicit user interruption message does. The official repeated-interruption recovery-exhaustion message is a failure, not a muted user stop. A retryable error does not itself claim retry is running.

Live feedback takes precedence over the failed attempt: `AssistantResponseStatus` suppresses the latest assistant's generic interruption while shutdown recovery is pending, and its error while authoritative retry is active. Older assistant errors and read-only history retain their own presentation. `SessionErrorNotice` likewise defers to live recovery/retry. `useAssistantStatus` never derives thinking/composing from an errored assistant or a previous turn's parts; errors settle the working hint immediately unless authoritative retry is active. Shutdown recovery has a separate flag: `StatusRowContainer` unmounts the ordinary working hint (including its linger/timer), while the Composer's `SessionRecoveryNotice` is the single current-status row, using the neutral restart icon and localized “Service restarted. Waiting to confirm task status.” It makes no promise of successful automatic continuation. The retained busy claim and cancellation/queue semantics remain sync-owned. New authoritative activity clears recovery and new assistant parts restore normal live feedback. Coverage: `useAssistantStatus.turnSettled.test.tsx`, `SessionRecoveryNotice.test.tsx`, and `SessionErrorNotice.test.tsx`.

Native synthetic `description: "Continuing after restart"` renders as a localized timeline notice until a later assistant row confirms resumed execution. `MessageList` retires superseded restart notices during display normalization using transcript source order, for both live output and reloaded history; a subsequent restart remains visible until its own continuation. The repository retains the synthetic record and its model-facing instruction, which stays hidden. Turn projection retains other visible synthetic notices in `turn.messages` in source order while excluding them from assistant lifecycle/activity and authored-user turn counts. `TurnAssistantBlock` interleaves notices with the visible assistants; notice changes invalidate only their owning turn. The notice never proves current activity, and a page reload alone does not fabricate it. Regression coverage includes GET projection, live/sorted desktop/mobile transcript rendering, settled history, repeated restart, icons, structured notification retention and all locale dictionaries.

## Native inbox configuration and shutdown recovery

Native queued inbox Edit restores the authoritative text, files, agents and skill references into the captured Composer draft through `session-inbox-edit.ts`, then cancels the pending inbox identity. Successful edits focus the Composer. Edit/Send/Remove on that chip are locked during the edit mutation; admitted steer items stay send-pending. Draft persistence must commit before cancellation. Definitive cancellation rejection uses revision-guarded rollback; an ambiguous network failure retains the recovered draft and reports failure. Session/runtime changes and unmount fence late work. Shared behavior applies to desktop, web, VS Code and mobile.

Native inbox chips preserve the compact queue presentation without execution-configuration hints. Enter defaults to queue admission; the primary Send button and queued-item Send action steer. A queued-item Send shows pending feedback immediately through its mutation, then stays pending while authoritative delivery is `steer`, until consumption removes the chip. Failed promotion restores the queued action. Native consumption still inherits session configuration; Host/Assistant captured queues retain their own configuration contracts.

Native queue submission stages a runtime/session-scoped `pending-admission` chip synchronously before selection flush or network work, using the prompt's fixed message ID. It reuses the existing localized “Queuing…” presentation. Authoritative inbox rows replace that presentation by the same identity without a duplicate. Early exit or failed submission clears the pending chip and restores the captured draft through the existing recovery path. `delivery: "queue"` skips both the Composer pre-await optimistic ticket and the send layer's transcript insertion / pending-user animation; only actual upstream consumption may put that user message in the transcript.

Existing queue items redirect a new Composer submission only during authoritative busy/retry or an active auto-review. Idle/unknown submissions send directly, and explicit steer bypasses that redirect. A direct submission with authored content does not merge or clear waiting queue items. Native inbox admission is not itself a queue presentation: only items observed with `delivery: "queue"` render queue chips; their `wasQueued` provenance survives promotion to steer until consumption. Direct steer admission stays off the queue surface.

`SessionRecoveryNotice` sits beside the queue surface near the Composer. It reads only the exact directory/session shutdown marker through `useDirectoryStore(directory, { bootstrap: false })` and a Zustand boolean selector. Primary chat supplies its resolved session directory; secondary surfaces supply their own directory. Failed connections preserve the confirmation notice until sync clears the marker; busy history alone supplies no notice or running animation. The leaf stays outside `QueuedMessageChips.trailing`, preserving the empty queue shell gate. Rendered coverage: `SessionRecoveryNotice.test.tsx` and `QueuedMessageChips.inbox.test.tsx`.

## Side questions (`/btw`)

Primary session composers expose the OpenChamber `/btw` candidate on desktop and mobile. `/btw` is in the auto-submit list: Enter/tap on the candidate opens the side conversation directly, because its draft lives in the panel composer. Hosted secondary composers retain their command policy and omit this primary-session presentation.

`btwCommand.ts` claims manual, pasted, keyboard and native/button submissions before main-turn flight, queue admission, prompt history, selection flush, or optimistic transcript work. Main-session busy/retry and an in-flight main send leave the side-question Send action available. Bare `/btw` clears the token and opens the panel without any request; `/btw <question>` also sends that question as the first turn through `useSessionBtwStore.ask`. Missing sessions retain the input and show a localized toast. Reference-bearing documents (including confirmed mentions) retain their complete draft and request plain text; accepted commands clear only the body, preserving root attachments, inline-comment drafts, queued messages and synthetic resources.

`layout/BtwPanel.tsx` is a self-contained Side Chat backed by OpenCode's native `session.generate` (request body is prompt-only; model/agent come from the parent session on the server). The panel composer is the same `ChatPromptComposer` pill as primary ChatInput: 1.5rem radius, stacked textarea, quote chips as `inputHeader`, read-only model label in the footer left, and the shared circular send/stop on the footer right. It does not invent a separate boxed field or put Send beside the placeholder. Phone and mobile-sheet feet add `oc-mobile-composer` (and `oc-mobile-composer-surface`) so the input follows the primary composer's page foot, including Android transform lift and iOS shell shrink. The phone page owns bottom safe area on that foot; the sheet does not add a second safe pad. While that web foot is the visible input, the iOS native composer overlay is concealed so it cannot cover the field; focusing `[data-btw-composer]` still runs the web keyboard path. The current model is display-only (no picker, no agent switch); before each turn the store calls `applySendSelection` with that session's current model. Attachments and queue are still unavailable on this API path (not on fork-based btw). It renders only the side turns (question bubble, shared Markdown answer, per-turn copy, retry on the last turn) and never loads the main session transcript. Send is Enter (IME-safe, Shift+Enter newline) and swaps to Stop while a turn is pending. Desktop uses the existing resizable/expandable ContextPanel with a transient `btw` tab; mobile uses the shared `MobileResizableSheet`. The main Composer focuses the panel composer after opening (`btwComposerFocus.ts`) and renders no btw chip of its own.

`message/TextSelectionMenu.tsx` offers exactly two selection actions: Add to Chat (`mod+l`; FilesView editor selections use the same shortcut) and Add to Side Chat (`mod+shift+s`, primary session only). On mobile the actions sit in a page-background foot that covers only the composer, so the transcript above stays selectable; the foot follows the composer box and keyboard overlap, including when the iOS native composer is concealed for the selection. It is not a half-sheet and does not dim the page. Desktop keeps the compact pill above the selection. Both stage the selection as a quote chip (`ComposerQuoteChips`) instead of inserting it into the draft text. A real send still prepends those quotes for the model, and the user bubble renders the same quotes as compact lines above the authored text (`splitQuotedConversationMessage`) so the selection stays visible after send. The optimistic row uses that prefixed text too; markdown rendering must not be the only place the selection appears, because user markdown escapes `>`. A real send prepends those quotes as `>` blocks and clears them; a failed send restores them; a slash command leaves them staged. Side Chat stages through `useSessionBtwStore.addQuote` and opens the panel through `openSessionBtw`; the next side turn consumes them the same way. Selection shortcuts listen in the capture phase only while a selection exists inside the transcript, so they take precedence over the global `mod+shift+s` services-menu binding only then.

The mounted primary Composer owns request lifetime. Leaving its active session/directory or unmounting cancels the in-flight turn; a microtask lease skips StrictMode same-scope rehearsal and protects a newer request. Closing the btw tab, the panel, or the mobile sheet clears the conversation. Selecting another desktop tab keeps it. Runtime resets remain store-owned. ## Question auto-delegation

Pending Question, Permission, and native Form interactions all render through

The Question card's explicit Dismiss action calls `session-actions.dismissQuestion`: interrupt the owning session with continuation disabled (`@opencode/client` 2.0.12 `resume: false`), letting OpenCode `Form.ask` cancel the form during user-interrupt cleanup. Never cancel a running question first: that path can terminate without an explicit user reason and be classified upstream as shutdown, leaving false recovery/busy chrome. Only an authoritative `interrupted: false` permits orphan-form cancellation. Failed stops leave the question actionable; live user-interrupt events own idle/recovery settlement. The send-path `rejectQuestion` remains the form-cancellation primitive. No queue-head promotion is performed by explicit question dismissal.

Native `FormCard` uses shared chip buttons for string options and semantic surface/border tokens. Its initialized answer matches the visible initial option; explicit custom string answers survive projection. Reply/cancel failures stay visible in the card and keep answers available for retry. The form remains in its existing composer location.

OpenCode question-tool forms (`metadata.kind === "question"`) render only as `QuestionCard`. Generic pending forms still use `FormCard` and do not repeat that question.

`QuestionCard` retains its question/session identity and existing parent-view subagent attribution. `QuestionAutoDelegateStatus` reads the runtime-scoped Query snapshot through `lib/questionAutoDelegate.ts`; pause and immediate delegate use the matching request's authoritative `sessionID` and `directory`. Drafts remain mounted. A stale or failed refresh keeps the result-pending presentation and offers status refresh. Other failures retain ordinary failure handling; submitting, uncertain, and settled authority states disable answer submission.

The countdown strip sits above the submit/dismiss row. A full-width `h-1` bar (`data-question-delegate-bar`) appears as soon as the card mounts **while automatic delegation is enabled** (default until the snapshot says otherwise); snapshot matching uses `requestID === question.id` and does not require `sessionID`. `snapshot.enabled === false` hides the bar immediately, including when this question is not yet listed. Until the snapshot provides `deadlineAt`, the bar is display-only from card mount (30s). `serverNow` plus a monotonic receipt timestamp then corrects remaining time. Only the countdown leaf ticks (250ms), with a transform-only progress transition and reduced-motion override. Reaching zero displays an awaiting-confirmation state. The server owns the 30-second timer and answer submission.

Pointer/click, keyboard, input, paste, and composition-start capture **immediately hold** the local countdown **and POST pause** with `reason: interaction` using the card's `question.id` / `sessionID` — they must not wait for GET/snapshot identity, or the server timer keeps running. Explicit pause uses `reason: user`. A pending request is single-flight; failed interaction pauses after a real transport error require an explicit retry. `QuestionAutoDelegateNotifications`, mounted alongside the transcript under SyncProvider, shows confirmed automatic reply feedback even after the card leaves the pending list. It uses a stable epoch/request toast ID, transition detection, and foreground visibility gating; background clients consume the new snapshot quietly. Separate simultaneously visible clients each own their local toast.

Reply history remains upstream-owned: `ToolPart` displays parsed Q&A from a completed question tool's string output. Missing or unparseable upstream output falls back to question input, so the actual auto-reply text may be unavailable in that history view. Delegation snapshots contain state and resolution only; the UI creates no synthetic answer/message from a success receipt.

Chat settings expose `questionAutoDelegateEnabled` (default true) through the existing `RuntimeAPIs.settings.save` and `chat.question-auto-delegate` search anchor. Tapping one approves only that image; slim fills still use one `session.message` request, but unclicked siblings stay gated until tapped. `data:`/`blob:`/`http(s)` URLs and unknown sizes never gate, and direct (non-Relay) transports keep unconditional auto-load. Compact user-message images render as square cards: one capped column, or two or more in a two-column row that wraps. `FileAttachment.tsx` owns the pure decisions (`messageSlimImageManualLoadRequired`, `filePartImageManualLoadRequired`, `filePartImageKnownBytes` preferring measured `byteSize` over declared `size`). Markdown images (`MarkdownRendererImpl`) carry no size metadata and stay auto-load; the full-screen viewer keeps its own Relay-resolved loading because it only opens on explicit click.

After a user send, the legend timeline enters `anchoring-new-turn`. `beginOptimisticSend` marks the pending send **before** it inserts the optimistic user row, so MessageList's render-phase consume sees the pending count on that same insert (ChatInput paints the row well before `sendMessage` runs). Pending is the send signal: consume parks the current last user row even if a sibling or earlier paint already recorded that id. MessageList passes that live `nextAnchorId` into the list on the same render — waiting on `useState` lets end maintenance pin the just-sent row to the bottom for a frame. The consumed id is remembered at module scope (`userSendAnimation`) so a React Strict Mode remount — fresh component state, pending count already zero — can re-latch the same send instead of treating the transcript as a session swap. That latch is not last-read memory: the primary list delayed-clears it on leave (`queueMicrotask` after layout unmount) so a same-turn remount can still peek and a later reopen cannot park on the old user row instead of `initialScrollAtEnd`. Idle renders and secondary transcripts (context panel `enableSendPark={false}`) must not consume or clear that remount latch. Occupancy is a trailing list item after that last turn (`resolveReplyReserveUpdate`: leftover of the chrome-aware middle window, capped at 40% of the list viewport, `getFixedItemSize` so the virtualizer can park immediately), not a `minHeight` on the turn and not a footer — collapse, hydration, and streaming keep writing the row's natural height through `resolveShrunkItemSizeUpdate`. On immersive mobile the list is the full screen, so usable height subtracts the measured header (safe area + floating nav) and footer (composer inset + tail); the parked row sits just below that header. There is exactly one bottom inset in that math — the measured footer. `TimelineList` previously also took a `composerOverlayHeight` prop that `resolveUsableViewportHeight` and `getAnchoredTurnMetrics` subtracted on top of the footer; every caller passed `0`, so it was a second name for the same quantity and an invitation to double-count it. `endInsetHeight` is now the only one. The hole is the live edge — there is no further downward scroll room under it. Distance, the scroll-to-bottom pill, and `--oc-native-composer-dock` all read that parked offset (`data-oc-timeline-park-end`), not `scrollHeight`. **That published offset is bounded by the scroll room that actually exists** (`resolveParkedLiveEdgeOffset` with `resolveMaxScrollOffset`). Because the hole is capped at 40% of the viewport, it is routinely smaller than the window the anchor offset asks for: on a phone (viewport 852, header 135, footer 290 ⇒ usable 427, cap 341) the scroller stops 86px short of the ideal offset right after a send and 46px short a few tokens later, closing only once the reply is ~120px tall. Publishing the ideal there let the platform silently clamp the park scroll and then reported the resting viewport as 86px from its own live edge — past both the 40px re-arm band and the 80px pill threshold — so the scroll-to-bottom control appeared at rest and the at-end re-arm was withheld until the reply grew, then both flipped. The one-shot park *scroll* deliberately still targets the unbounded ideal, since the scroller clamps a too-far target itself while a content length that has not counted the fresh hole yet would park short and stay there. **Nothing corrects the position toward the parked edge on scroll.** The hole makes that offset the end of the content, so the scroller's own bounds hold it and a touch surface keeps its native rubber-band; a per-frame correction read iOS overscroll `scrollTop` (which passes the maximum mid-bounce) as "scrolled past the edge" and wrote scroll under a live gesture, felt as the transcript fighting the finger. Slack below the edge only opens as the reserve is being dropped, which returns to `following-end` regardless. Live status (`StatusRow` / 正在发送消息 / 思考中) stays inside the newest turn row so the reserve cannot push it to the bottom; the legend footer keeps only questions, permissions, and the composer inset. The working hint uses the same last-assistant `hasConfirmedFinalBody` settle as Changes chrome and unmounts in that commit (no 600ms step-gap linger), so it cannot flash after the turn is already done. The spacer starts as that capped hole and shrinks as the turn grows; a same-row collapse that would reopen it or overflow (`isReplyReserveOverflowing`) drops the reserve, clears the remount latch, and returns to `following-end`. Jump-to-latest returns to the parked offset and keeps the hole. A taller usable viewport (keyboard dismiss) keeps filling the hole up to the cap instead of dropping the park; an unmeasured (`0`) viewport must not wipe an already-seeded reserve. The list parks the row `CHAT_LIST_ANCHOR_OFFSET` from the top once per send (`reserveId` is the user-message id, so an ungrouped `msg:` row becoming a `turn:` relatches the spacer instead of treating that as a collapse). Composer send re-arms follow so a send from mid-history still parks. The TanStack fallback still force-pins to the bottom on send.

On mobile, history availability is owned by QueryCache / TranscriptRepository pagination (`SessionHistoryBoundary`: `unknown` / `has-more(cursor, loadedTurns)` / `exhausted(loadedTurns)`). `ChatContainer` reads it through `useSessionTranscriptPagination`, so a boundary-only repository commit re-renders the container and converges the history entry immediately without a broad child-store subscription. A `has-more` boundary enables the localized load-older action; `exhausted` removes it; `unknown` renders nothing — never a speculative placeholder or spinner, with background initial/SWR pulls owning convergence to a known boundary. `historyMeta` derives straight from the boundary: unknown → `complete:false`/`canLoadEarlier:false`/`limit 0`; has-more → `canLoadEarlier:true` + `loadedTurns`; exhausted → live `complete:true` + `loadedTurns`, and the assistant archive (when present and incomplete) may still page after live exhaustion. The button exists only while `canLoadEarlier` is true or a real user-initiated loadEarlier mutation is in flight; that flight keeps the button painted so its spinner has an anchor. Load-more busy stays mutation-owned: background ensure/SWR loading never paints or busies the button, and repository request state contributes loading/error to transcript hydration only — never cursor/complete/limit facts. Timeline `historyMeta.loading` (the concurrent-page wait gate in `fetchOlderHistory`) is repository/sync load state `|| assistantHistory.loading` only (`resolveChatHistoryPaginationLoading`); stuck background loading must never block user-initiated `fetchTranscriptPreviousPage`. The context-panel transcript derives its load-older entry the same way (`resolveContextPanelHasMore` on repository pagination for the same scoped session), and its button spinner stays mutation-owned; both surfaces call `fetchTranscriptPreviousPage` for live prepend. An explicit history interaction holds auto-follow released through its keyed viewport restoration, so TanStack transition and measurement scroll events cannot claim bottom ownership during the transaction. Its layout effect brings the same keyed virtual row into range and restores the message's exact viewport offset before paint. This transition-local correction runs at most once and keeps TanStack core as the owner of ordinary virtualized prepend and measurement compensation.
