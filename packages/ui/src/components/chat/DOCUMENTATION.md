Sorted compaction turns use the turn-owned Activity visual language with a dedicated `fold-vertical` icon. Active compaction shows localized Compacting text, the shared info-token shimmer, and live elapsed time; normal and abnormal completion show localized Compaction complete text with authoritative `turn.durationMs`. Before any assistant message arrives, `TurnItem` supplies a status-only header (`shouldShowCompactionStatus`): settled (`normal`/`abnormal`) without assistants still qualifies, while `active` is gated by the last turn plus the authoritative live `sessionIsWorking` signal so history pagination or partial loads cannot paint a stale Compacting state on idle or older turns. Once assistant messages exist, `MessageBody` owns the Activity disclosure on the activity-owner message even when there are no tool/reasoning segments: summary body text folds under that header when the turn is collapsed (`activityRenderMode=collapsed` or an explicit collapse), and expands with the ordinary per-turn toggle. Status-only (non-disclosure) remains only while compacting with nothing foldable yet. Live mode and default turns keep their established paths.

Slash-command autocomplete auto-submit is name-whitelisted in `commandSelection.ts` (`AUTO_SUBMIT_SLASH_COMMANDS`: `new`, `fork`, `compact`, `undo`, `redo`, `model`, `goal`). Enter/tap on that short list runs the local action immediately (`/model` opens the model selector; `/goal` only arms). Everything else — custom/opencode commands such as `/loop`, magic prompts, `/timeline`, `/init`, skills — only inserts into the composer so the user can keep typing or confirm with a second Enter. `/goal` is arm-only: it flips goal mode, strips the slash token, leaves any trailing objective draft in the composer, and never auto-sends. Hand-typed complete slash tokens are promoted to reserved-slot chips (`/\u2003name`) in `typedSlashChipPromotion.ts` so icon spacing matches autocomplete selection; autocomplete query parsing strips that slot so ranking still keys off the bare name.

Current best-effort policy: direct submit and legacy queue admission use captured attachment views immediately. Attachment clear, failed-send restore, and queue cleanup results stay outside the send/admission gate. Sent chips clear from memory while persistence continues in the background; restoration errors are allowed.

Queue actions use server admission after authoritative active or paused ownership for the current transport, including a lagging `probing` cutover publication. Shadow, blocked, wrong-transport, and otherwise unconfirmed ownership keep queue mutations frozen; a busy Composer submit falls back to captured-session `steer` so the running turn remains interactive. Submission identity gates still disable unsafe targeting. An in-flight queue admission is visible and permits later send, admission, edit, remove, manual promotion, and reorder actions. Composer `submissionFlightKind='queue'` keeps the floating queue control visible with a queuing spinner (`queuingMessageAria`) after the body clears so admission still feels immediate. Pending-admission chips show spinner plus `chat.queuedMessage.queuing` text until the authoritative row replaces them. After server admission commits, body consumption compares the captured Composer document with the current live document rather than DraftRecord object identity or persistence timing; identical delayed hydration cannot restore an admitted body, while any continued authored edit changes the document fingerprint and remains in the Composer. Attachments and inline drafts retain their independent occurrence/fingerprint checks.

`ChatContainer` accepts an optional `host` (`chatContainerHost.ts`) for embedded transcripts. Hosted mode skips the primary session-view cache, injects session/directory/composer surface/`SessionSurfaceContext`, merges `onRevertMessage` into that surface so message actions and the timeline restore into the host draft partition, and disables primary-only draft/prompt-navigator/return-to-parent features unless explicitly re-enabled.

A primary staged message edit is visible on its own row before send: `ChatMessage` reads `stagedMessageEdit` / `messageEditCommitting` from the session UI store and `MessageBody` replaces that user row's action group — keeping the row geometry — with a highlighted `editStaged` label plus a cancel affordance, then with a shimmering `editing` label once the commit is in flight. Neither state hides or removes any existing row, so the optimistic user row for the resend paints independently. Staging is disarmed by the row's cancel affordance, by leaving the session, and by the Composer losing focus. A disarmed edit makes the next send an ordinary message that deletes nothing. Staging focuses the Composer textarea once per staged row (retried on the next frame when the node is not yet mounted or still disabled) so the restored text can be edited without a second tap. The paint is released by the commit, by the settle of the send promise, and by the non-handoff `finally`, and `endMessageEditCommit` only clears a matching session/message pair, so the redundant releases are safe. Hosted continuous Assistants inject `onEditMessage` so sent-message edit stages into the surface `DraftKey` (`surfaceDraftKey`) and a per-assistant entry owned by `assistantStagedMessageEdit.ts`. The registry scopes entries by `transport + assistantID`, serializes stage and best-effort rollback cleanup per scope, and keeps primary `stagedMessageEdit` untouched. Assistant send synchronously clears its staged marker and delivers the restored Composer content as a new message through the ordinary path. Runtime and binding changes may attempt CAS rollback in the background; failures retain the restored draft until a later user action replaces or clears it. Assistant `resources.attachments` project root DraftRecord attachments only; synthetic parts restore merge by partID and never double-send via root attachments.

Assistant send clears the staged restoration marker and follows the ordinary delivery path. Restored content is sent as a new message, so staged history mutation cannot block delivery.

History segments remain read-only (`mutateSession: false` on source-scoped surfaces). Stateless Assistants omit `onEditMessage`.

Hosted Assistant history uses the Assistant HTTP infinite query instead of per-session sync materialization. Its key and request closure capture transport identity plus runtime generation, and validate currentness before and after every page request. It preserves server `Message`/`Part` references plus source session and nullable directory while adding semantic session dividers ahead of the live binding. Each historical message with a source session receives a source-scoped read-only `SessionSurfaceContext`; known directories scope file paths, tool actions, and source-session navigation to the archived workspace, while unknown legacy directories keep these directory-dependent actions unavailable. The shared timeline controller loads current-session sync history first and then asks the host for the next Assistant history page, so desktop near-top loading and the mobile button share one completion/loading signal through small and empty cursor pages.

Desktop older-history loading is owned by `useChatTimelineController` with gates in `shouldLoadEarlierHistory`. Ordinary scroll never loads while auto-follow is pinned; explicit upward intent (wheel/touch/key via `useChatAutoFollow` `onUpwardUserIntent`, bridged through a ref in `ChatContainer`) may bypass a stale pin so a gesture at `scrollTop === 0` still loads without a scroll event. Nested ancestors that still have upward scroll room (`scrollTop > 0` and overflow content, detected by a shallow walk from the event target) and overlay-scrollbar pointer drags do not fire that intent. Mobile never auto-loads from scroll or gesture — only the explicit top "load older" button. Product **`limit` is authored-user turns** (local/LAN: initial 6 / prepend 2; Relay: 2 / 2), not message count — Host turn-page windows via `session-message-policy.ts` and `isRelayModeActive()`. History meta `limit` accumulates turns. Each user-initiated interaction issues at most one server turn-page request (`HISTORY_INTERACTION_MAX_PAGES = 1`). Collapsed turns can absorb a page without growing `scrollHeight`; `resolveHistoryPageDecision` uses turn-limit growth, not message counts. `isLoadingOlderRef` is armed synchronously at fetch start so concurrent wheel events cannot open parallel pagination chains; `fetchOlderHistory` also refuses to start while `historyLoading` is true.

When the active desktop transcript paints shorter than the viewport (`scrollHeight ≤ clientHeight + 48`) while still auto-follow pinned and `historyMeta.canLoadEarlier` is true, short-viewport auto-fill is **TanStack Query-owned** (`chatTimelineAutoFillQueryKey` + `useQuery`, not a `useEffect` dependency chain). Layout publishes viewport metrics; `enabled` gates on those metrics plus pin/cursor readiness; the query key moves with the timeline edge (`oldestMessageId` / count) so a successful short page re-arms without effect ordering races. Transient `historyLoading` / in-flight older loads throw a busy code and retry; no-growth or hard failure sets session `autoFillBlocked`. Handlers use `@reactuses/core` `useEvent`; unmount cleanup uses `useUnmount`; DOM scroll compensation stays on `useIsomorphicLayoutEffect` (pre-paint geometry). Auto-fill keeps auto-follow pinned (never `userInitiated` / `releaseAutoFollow`). `historyMeta.complete` is only true after sync positively reports live complete (and assistant archive complete when present); a missing cursor is neither complete nor loadable.

History viewport restore arms a pre-fetch snapshot, but **ownership splits by engine**: virtualized history (`resolveHistoryPrependCompensation` → `tanstack-core`) leaves scroll entirely to TanStack end-anchor (`anchorTo: 'end'`, measure/resize compensation) — the controller must not also run `heightDelta`, `restoreViewportAnchor`, or a multi-frame `holdViewportAnchor` on that path (those dual writers produced multi-thousand-px load-more jumps with no user input). Non-virtual lists keep one-shot absolute anchor restore or `scrollHeight` delta. `shouldHoldHistoryViewportAnchor` is always false. `MessageListHandle` still exposes `holdViewportAnchor` / `cancelViewportAnchorHold` for cleanup; session change and virtualized snapshot commits cancel any leftover hold. `releaseSnapshot` clears the armed snapshot only while it still owns it so a superseded interaction cannot cancel another owner's state.

Hosted surfaces may provide stable-ID pending user-message presentations. `ChatContainer` appends each pending row through the standard MessageList path, keeps it visible across host binding changes, and lets an authoritative current/history row with the same message ID replace it. Assistant admission atomically rebinds that pending identity to a stateless result session, then runs bounded background materialization retries. Admission success remains final for the Composer; materialized IDs or the bounded retention deadline release pending attachment data. Rejected admission removes its pending row while the Composer restores the captured submission. Assistant session loading uses `ensureSessionRenderable` as its single authoritative materialization path.

Hosted current-session merge (`mergeHostedCurrentSessionHistory`) seeds from Assistant SQLite for the live binding, then overlays directory-sync rows by message ID. Live wins only when it carries parts; a part-less live row must not wipe SQLite provisional admission parts — user bubbles render as empty (`displayParts.length === 0` → `null`) and would otherwise disappear until refresh. Pending presentations still stand in when neither source has parts yet. Assistant history infinite queries keep same-assistant placeholder data across binding key changes (`sessionID` / `sessionGeneration`) so a stateless turn does not blank the stitched transcript while the new key loads; assistant/runtime switches stay cold.

`MessageList`'s `renderMessage` and `renderEntry` are render props — `TurnAssistantBlock` calls them while rendering — so they use `useRenderPhaseCallback`, never `useEvent`. `useEvent` refreshes its handler ref in a layout effect, one commit after the render that changed the closure, so a turn that just grew resolved its new message against the previous render's `visibleAssistantIds`. The lookup missed, `assistantIndex` came back `-1`, and the message fell through the assistant branch entirely: no `turnGroupingContext`, so it rendered as a standalone assistant with its own model header and the between-turns `pb-8` gap instead of joining the turn. Because `TurnItem` is memoized on the turn, that render committed permanently once the stream ended. `useRenderPhaseCallback` writes its ref during render, keeping one identity for the memo while always dispatching to the current closure.

Virtualized rows defer rich Markdown, and `markdownHydrationWindow.ts` decides which rows may hydrate in the next commit. Preload reaches `resolveMarkdownPreloadEntries(activityRenderMode, visibleCount)` rows past both edges of the viewport, ordered by travel direction, so a row is normally hydrated before it is ever painted; hydration that only starts once a row is on screen guarantees a visible placeholder-to-Markdown swap. Collapsed activity packs more turns into the viewport, so the preload floor is higher (`MARKDOWN_PRELOAD_ENTRIES_COLLAPSED`) and never narrower than the visible range — otherwise a fast upward fling paints skeletons that then remeasure and yank scroll. Scrolling withholds visible rows and meters off-screen preload (`resolveMarkdownPreloadReleaseWhileScrolling`: 2 while collapsed, 1 otherwise). Cold open and bulk history land settle the full current visible window in one after-paint commit (no `startTransition`) so end-anchor does not remeasure and scroll-correct once per metered row — a multi-step 4-row idle release showed up as ~1s of Layout + ScrollLayer pairs in load traces. After that first settle, idle frames meter under `resolveMarkdownVisibleReleaseLimit` (4 collapsed / 6 summary) so a dense collapsed viewport cannot freeze a ~480ms ChatMessage dump. Remaining visible rows continue on later idle frames; one-per-row release is still avoided because each partial batch remeasures together.

History virtualization uses `@tanstack/react-virtual` (pinned with `@tanstack/virtual-core`) in end-anchored chat mode: `anchorTo: 'end'`, `followOnAppend: true`, and `scrollEndThreshold` (80px) so prepends keep the keyed viewport stable, appends follow only while pinned, and last-row streaming growth pins via the core `wasAtEnd` path. Jump-to-latest calls `scrollToEnd()`. Size-change compensation uses the virtual-core default (3.17.6+): first measure any above-fold estimate→actual delta; remeasure only rows fully above the fold; skip while scrolling backward — app code does not reassign `shouldAdjustScrollPositionOnItemSizeChange`. While `wasAtEnd`, core still calls `scrollToFn` once per measured row; `coalesceVirtualizerScrollTo` collapses that measure wave into one height + `scrollTop` write per task so cold open does not thrash Layout/ScrollLayer N times. A small root patch still clamps the render-range scroll offset to real bounds during transient adjustments. Cold estimates remain activity-density aware (`resolveTanstackEstimatedEntrySize`): summary defaults to a tall turn (~320px), collapsed to a short disclosure (~168px). An overestimate on every newly mounted row during upward scroll triggers first-measurement `scrollTop` corrections that re-enter the scroll handler and read as flicker. Overscan therefore mounts in at most two waves (`historyOverscan.ts`): first paint up to 8, then a single jump to the product overscan (mobile 16) — not a 2→4→6→8 ramp. Timeline measurement snapshots are keyed by `resolveTimelineVirtualizerCacheKey(virtualizerKey, activityRenderMode)` so collapsed and summary geometry never cross-seed. The adaptive average also converges with fewer samples while collapsed (`resolveTanstackEstimateMinSamples`). App-level `useChatAutoFollow` still owns composer/content observers outside the virtualizer count/measure path.

`markdownHeightCache.ts` records the height each content string actually rendered at, and the deferred placeholder in `MarkdownRenderer` reserves that box instead of laying out the Markdown source as an invisible spacer. Rendered Markdown is far shorter than its source — fenced code, link targets and table pipes all collapse — so the plain-text fallback overshoots and the swap into real content shrinks the row, which the virtualizer then compensates by yanking the scroll offset. Heights come from `ResizeObserver` entries rather than a measured read, keeping a batch of rows revealing together from thrashing layout, and are recorded only for a settled non-streaming render. Only the rich renderer records and reserves; the simple renderer produces different output for the same source. Every entry is dropped when the column is next measured at a new width, because one width applies to the whole transcript.

Every entry point into the Shiki worker — `highlightCodeInWorker`, `highlightLinesInWorker`, `highlightTokensInWorker` — is memoized in `markdownHighlightCache.ts` and owns that caching for all callers, including the file and diff surfaces. Keys are content-addressed (language, plus theme name for token runs, plus the code itself) rather than derived from a message or block position, because `markdownCore`'s per-block cache is keyed by part id and block index and therefore misses whenever a message re-segments or history scrolls far enough to evict it. Concurrent requests for the same snippet share one worker job, and the job is cancelled only once every caller has abandoned it, so a row scrolling out of view cannot strip highlighting from a row still waiting on the same code. Failed highlighting resolves to `null` and is never cached, keeping a worker outage retryable.

A fence whose info string is a `startLine:endLine:filepath` code reference is split by `codeFenceInfo.ts` into the Shiki language id to tokenize with — resolved from the referenced file's name or extension — and the label shown on the code card header. The two cannot be the same string: the id has to be lowercased to match Shiki's registry, and the whole triple matches no grammar at all, so treating it as a language leaves every reference block uncolored under a mangled path. The highlight pass stamps `data-md-label` alongside `data-md-lang` only for references, so plain fences still morph to the markup they had before; `decorate.ts` prefers that label and otherwise parses the `language-*` class marked emits, which is all the synchronous first paint has. A bare `mermaid` fence stays unhighlighted for the diagram pass, but a reference to a `.mmd` file is source and colors like any other.
