# Assistant UI

## Acceptance criteria

The Assistant conversation is a Grok-like **contact**, not an OpenCode coding agent. Primary Chat still owns LegendList / Activity / tools. Assistant must not wrap `ChatContainer` as its transcript.

**Session cards (this PR)**

- Cards are first-class in-transcript UI (`type: 'card'`, `cardType` `session` | `assistant` | `schedule`), not markdown links and not Activity/tool rows.
- A session card is a compact cover: short title, one metadata line (project / model / branch), status chip (`Working` / `完成` / `失败` / `需要你`), and non-zero live change counts (`summary.additions` / `deletions` / `files`). `+0 −0` and other all-zero summaries stay off. Assistant/schedule covers hug content (`w-fit`, 15rem max); session covers may be wider (20rem max) but are not a full-width strip. The whole card is the hit target and opens the session through `openSessionWithFeedback` (phone: `openSession`; desktop: `setActiveMainTab('chat')` + `setCurrentSession` / `/session/$id`). No visible CTA button.
- Assigned-session finish/error/question (SSE, session-goal settle, or boot/60s poll of in-flight watches) updates **that same card** plus a settle bubble. The UI does not invent a second status banner. The worker session stays visible in Chat.
- Cards persist in the OpenChamber-owned contact transcript (SQLite) and survive reload.
- Contact attach is required: images and non-image files via paperclip, paste, and drag-drop. File parts persist in the same contact transcript (`{ type: 'file', mime, url, filename? }` data URLs — the existing OpenCode delivery convention, not a second store). Images render inline in the bubble; other files render as a named chip. The contact harness forwards those parts to the OpenChamber Chat Completions / OpenCode provider gateway.
- The card slot is extensible. Later project / worktree / watch cards reuse `cardType`. Do not invent a second card system.
- Cards are **assistant-emitted UI** (Grok-Bot style: title, status chip, metadata). The whole card is the hit target. The user never types `/card`. Insert: `assign_session` / `create_assistant` / `schedule_task` auto-cards, and API `POST /api/openchamber/assistants/:id/contact/cards` for harness/tests.
- Assistant cards open that contact (`openAssistant`). Schedule cards open Scheduled Tasks. Session cards still open the worker session.

**Inter-assistant DM (this PR, read-only)**

- Assistant A can deliver a message to assistant B by name or `assistantID`. Natural Chinese (`给 PeerQA 说一声 …`) calls the `message_assistant` contact tool, which uses `POST /:fromID/contact/dm` `{ toAssistantID, text, parts? }`. The user never types `/dm`.
- Delivery is **read-only coordination**: it inserts text (and later cards) into B’s OpenChamber contact transcript only. It must not call OpenCode `session.promptAsync`, mutate B’s sessions/files/worktrees, or run tools on B’s behalf.
- The user sees inbound peer rows in the contact UI, visually distinct from user and assistant turns (`role: 'peer'`).
- Peer rows persist in the same contact store as user/assistant bubbles and session cards.
- This is the inbox primitive. Assign opens a worker session on the sender contact turn and auto-inserts a session card — it must not go through this DM channel. Full summon-to-work and unsolicited user pushes stay out; when they land they must use cards + this DM path.

`GET /api/openchamber/assistants/capability` still hides navigation when Assistants are disabled.

---

Assistant history entries require `{ sessionID, directory, info, parts }`, where `directory` is `string | null`. The UI retains the server `Message` and `Part` objects, validates entry/message/part session and message identity, renders paged history from oldest to newest, and opens historical sessions when their entry directory is known. Unknown legacy directories retain a null source context, which keeps workspace-dependent source and file actions unavailable.

Assistant names whose first grapheme is an emoji use that grapheme as their avatar across the Assistant workspace and Settings. The visible name omits the leading emoji while the stored name remains intact for editing and synchronization. Emoji avatars render at three quarters of the avatar box so compound glyphs stay within the existing layout.

The Assistant UI owns the current-runtime Assistant surface. Its product information architecture is an assistant list plus the selected assistant’s **contact** conversation. Desktop uses a flat Scheduled Tasks-style workspace: a soft left assistant list beside the conversation (no nested sidebar chrome), with elevated selected rows and a light border between panes. Phone navigation makes that hierarchy explicit: the Assistant root tab is a content-height catalog where every Assistant owns an independent shared floating-surface card, and choosing a card opens its full-width conversation as the shared second-level mobile page. Assistant list cards reuse the Project card title/meta typography tokens so names and one-line mode/prompt subtitles retain the same compact hierarchy across tabs. The conversation header owns Back plus the selected Assistant identity; it does not duplicate selection in a trailing picker. On phone it uses the same overlay `MobileDetailNavigation` fade as session chat so the transcript scrolls under a translucent gradient, not an in-flow opaque bar. The root tab owns vertical catalog scrolling and hides native scrollbar chrome, while the conversation owns only its transcript scroll. Each Assistant DTO carries `mode` (`continuous` | `stateless`), the current `sessionID`, `sessionGeneration`, a bounded compatibility `historySessionIDs` window, and `historySessionCount`.

Working status is a **small green dot** on the bottom-right of the assistant avatar in the contact list, conversation header, and transcript (`AssistantWorkingAvatar`, `data-assistant-working-dot`). The avatar and dot share a fixed-size relative wrapper so the marker cannot drift with flex/text baseline. Busy session cards reuse the same anchored dot on the card icon. It is ON while a contact turn is sending or an assigned session watch is still `busy` (or live session status is busy/retry). It is OFF when idle. This is Grok-Bot contact language, not an OpenCode Activity banner.

`AssistantConversationSurface` is the contact transcript: short bubbles, first-class session cards, and inbound peer DMs. User text stays the primary orange bubble; assistant text uses `surface-muted` plus a light border so replies read as bubbles against `bg-background` (elevated-only fill blends into the canvas); peer keeps a dashed muted bubble. It does **not** host `ChatContainer`, Activity, tools, or thinking. Assign tool results appear as those same bubbles/cards, not OpenCode Activity. The composer reuses the shared `ChatPromptComposer` / `ChatComposerSurface` shell in `layout="inline"` — one compact ~48px idle row with paperclip on the left, a textarea that fills that rail (`h-12` + `py-[14px]` / `leading-5` so the placeholder centers with the size-8 icons), and Chat’s filled `SendCircleIcon` (`data-composer-send`, `bg-foreground`) on the right in ready / muted-empty / spinning-busy states. No empty footer band. It grows with multiline text (`max-h-32`). Still a message box only: no `ChatInput`, slash commands, model/agent picker, or `/card` / `/dm`. Attach (paperclip + paste + drag-drop for images and files) is required and reuses `ChatPromptComposer` `onAddFiles`. Mobile applies `oc-mobile-composer-surface` and `bottom-safe-area`; it does not copy the Chat pill-swap or `MobileFloatingSurface` catalog card. Composer send appends the user bubble (text + file previews) immediately, clears the composer, and keeps a per-turn sending/failed marker. A synchronous send lock plus “already sending” ignore double Enter / form+Enter so one submit creates one optimistic turn and one POST. The contact POST uses an AbortSignal at 95s (just above server `GENERATE_TIMEOUT_MS` 90s). Abort marks the optimistic turn `failed` with `assistants.contact.timedOut` unless a 502 body already supplied `error.message`. Success reconciles that client `oc_contact_*` id after the contact refetch. The composer stays clear. The LLM gateway is still non-streaming. Settings still owns assistant create/edit/delete and model selection.

Pending capability or snapshot uses a spinner (`common.loading`), never `assistants.state.unavailable`. A `/assistant/$id` selection whose assistant is missing stays loading until the snapshot settles. Unavailable is only for error, unsupported, disabled, or a missing assistant after that success. The mobile catalog skeleton uses the same loading label.

Legacy OpenCode binding, share, and queued `promptAsync` paths remain server-side for share/queue. Assign uses `promptAsync` only on the dedicated worker session. They are not the user-visible contact thread.

`AssistantConversationSurface` previously hosted the shared `ChatContainer` shell. That path is retired for Assistant. It injects the Assistant session/directory, secondary `ChatInput` surface, embedded `SessionSurfaceContext`, and host `onRevertMessage` / continuous-only `onEditMessage` so message/timeline revert and sent-message edit restore into the Assistant draft partition (`surfaceDraftKey`). Continuous staged edits are owned by `assistantStagedMessageEdit.ts`, scoped by `transport + assistantID`, and serialized per scope for stage and best-effort rollback cleanup. `AssistantView` uses `stageExclusive` for continuous edit while primary `stagedMessageEdit` remains untouched. Staging retains an opaque CAS rollback handle for binding and runtime cleanup. Assistant send synchronously clears its staged marker and delivers the restored Composer content through the ordinary new-message path.

Revert success and successful `/new`/compact/shortcut-new intentionally clear the staged identity only (no pre-stage draft rollback): those paths are user-explicit history/binding replacements that already restore or replace the composer body through the existing command/revert consumption path; rolling back the pre-edit draft would fight that intentional replacement. Remote create/compact failure retains the stage. Stateless Assistants set `mutateSession: false` and omit `onEditMessage`, which removes edit/revert from message and timeline actions; continuous Assistants keep mutation. History segments stay read-only via source-scoped surfaces. Task and subagent rows use the same destinations as primary chat: desktop and iPad open the nested session in the right-hand `ContextPanel` (AssistantView mounts it with the assistant workspace directory), while phone, mobile web, and VS Code redirect into that session. Archived history rows keep nested navigation while remaining non-mutable. The surface also provides `openSourceSession`, so each Assistant reply can jump into its underlying OpenCode session in Chat for follow-up. On the dedicated mobile phone shell (Capacitor phone and hosted H5), that jump mounts chat through `useMobileNavigationStore.openSession` — the same secondary-route contract as scheduled-task history open — because `setActiveMainTab('chat')` alone does not mount the phone chat page. Desktop and iPad keep the main-tab + `setCurrentSession` path. The transcript uses the same MessageList / StatusRow / question-permission / timeline / auto-follow path as primary chat; Assistant does not keep a forked rendering tree. Assistant-only ownership stays in `AssistantView` (list, selection, binding, admission). `AssistantView` owns the complete secondary surface identity, scoped draft resources, scoped provider/model/agent/variant catalog (agents filtered via shared `chatComposerCatalog` / `filterVisibleAgents`), binding backend, command policy, activity, and shortcuts. Global Ctrl+X leader chords and agent-cycle hotkeys target the active mounted composer surface (`activeChatInputSurface`), not the primary chat tab alone. Assistant drafts and attachments use a stable transport-scoped `surfaceDraftKey` partition per Assistant. Selection PATCHes use latest-wins serialization keyed by Assistant ID, transport identity, and runtime generation; identity activation establishes the authoritative caller identity, while stale enqueue and flush callers reject with `AssistantSelectionStaleError`. Each selection flight owns an `AbortController`; retirement, disposal, and identity activation abort its in-flight conflict refresh. The selection backend verifies that identity before conflict refreshes and retries, then verifies it again after every asynchronous refresh boundary. Identity changes reject active selection and flush waiters as stale and isolate the new selection flight. A provider or model change clears the variant. Selection PATCH busy must not disable the composer textarea — Tab agent cycling stays focus-stable like primary chat. Hosted secondary composers must not block send on a missing directory session-list entity: the Assistant binding is authoritative, and mobile share/new often rebinds before the managed-workspace index has the row. When the session is busy, follow-up “queue” only admits through the server-backed queue; legacy/frozen ownership falls back to steer so share-busy turns stay sendable. ChatInput flushes the selection before direct or queued delivery. Assistant commands retain standard custom and skill routing; fork, thread, and branch commands are unavailable. Assistant SQLite owns admitted message durability; OpenCode sync owns richer live message content and replaces the matching SQLite fallback.

The current availability policy is authoritative for staged send behavior: sent-message restoration is best-effort. Assistant send clears the staged marker and delivers the captured Composer content through the ordinary new-message path; restoration state never gates delivery. The registry has no commit-before-send operation.

An admitted composer send completes immediately while bounded background materialization retries refresh its returned binding. The stable-ID pending user row remains visible until the same message ID appears in authoritative live or Assistant history, an explicit send failure removes it, or the runtime/component lifecycle releases the local surface state. Runtime changes retire delayed refresh work and clear every pending Assistant row.

Supported and enabled instances with an empty catalog show onboarding. The primary action opens Settings → Assistants, records a create intent, and focuses the assistant name field after the settings page mounts. Successful creation invalidates the Assistant snapshot; the still-mounted Assistant surface selects the new first assistant after Settings closes. Pending catalog reads stay on the loading spinner. Unsupported, disabled, transport-error, stale-data, assistant-disabled, and invalid-model states remain distinct from that spinner.

On native iOS and Android only, the first supported, enabled Assistant-page visit shows `AssistantShareWelcome`. It is dismissed per device with `openchamber:assistant-share-welcome:v1`; the dialog explains the iOS Share Sheet, Android Direct Share, and selecting an Assistant target that receives shared content in its Inbox Topic. Settings can reopen the same dialog from the Assistants sidebar “Learn more” / “查看更多” control on any surface. On iOS, an admitted Assistant composer send donates an `INSendMessageIntent` through the native share bridge with identity and generated avatar metadata only; message content stays out of the donation. Share Extension submissions perform the same donation inside the extension, and suggested-recipient launches route by the donated `conversationIdentifier`.

`queries/assistantQueries.ts` is the current-instance HTTP and TanStack Query boundary. Snapshot and capability keys begin with the active runtime transport identity. `fetchAssistantSnapshot(signal)` performs an abortable direct snapshot read for stale selection-conflict recovery; it parses the route response without Query cache writes or retries. Ensure and new return `SessionBinding`; compact returns `{ binding, summarized: true }`; messages return `{ binding, messageID, admitted: true }`. Snapshot hooks listen to the shared `openchamber:assistants-changed` revision tip and invalidate only their exact runtime snapshot; returned bindings older than the cached Assistant generation are ignored. Assistant history uses a transport-, Assistant-, and binding-scoped `useInfiniteQuery` over `GET assistants/:id/messages?before=&limit=`. Both the history `queryFn` and `ensureAssistantSession` capture transport identity and runtime generation first, wait for `waitForSessionStartupBarrier()` before any network request, then re-assert that the captured identity is still current so a barrier-held boot cannot silently rewrite the flight onto another runtime. The surface reads one persisted history page initially, retains each server `Message`/`Part` plus its source session ID, inserts the existing session dividers before the current binding, and merges current-session SQLite rows with live messages by stable message ID. Timeline loading exhausts the live session sync page first, then requests the next Assistant history page only after live pagination is complete. History host `loading` is initial/next-page fetch only (not background refetch); `complete` is true when there is no next page or the history query has errored so load-older cannot spin forever. When assistant-owned history rows are already rendered, a live-session prefetch failure must not replace the transcript with the chat history load-failure wall. A share operation carries top-level `sessionID` and `messageID` plus its persisted state, phase, attempt, lease, and error fields. It polls `share-operations/:operationID` with its captured runtime identity and generation; only `completed` settles delivery, while `failed` and `unresolved` retain structured errors. A consumer that needs a completed share binding reads a fresh Assistant snapshot or calls ensure. `AssistantView` calls ensure only while the active Assistant has no authoritative snapshot binding; an existing binding proceeds directly to session materialization. Assistant activity and streaming presentation derive from the scoped standard OpenCode sync state after HTTP admission. Ordinary message admission uses a soft `ensureSessionRenderable` so the transcript updates in place from live sync; force rematerialization is reserved for `/new`, compact, and explicit retry. Full-body loading only covers cold empty transcripts, never a background refresh of an already-rendered conversation.

`stores/useAssistantUIStore.ts` owns current-runtime assistant selection, the transient Settings create-request revision, the client-global default share identity (`serverInstanceID + assistantID`), and persisted complete Assistant catalog partitions keyed by connection key. Persisted selection stores only the assistant ID. `MobileShareBridge` validates share targets after runtime switches, reads a fresh Assistant DTO, dispatches by assistant ID, and opens that assistant. Generic Android shares remain unassigned in native durable storage until the full-screen in-app recipient page assigns an enabled Assistant from the persisted catalog; this selector is a complete page using the shared `MobileDetailNavigation` secondary-page treatment, not a bottom sheet or a locally recreated bordered header. Android Direct Share retains its native exact target and bypasses the picker. Android share-draft handoff journals its exact assigned runtime target through `materializing`, `materialized`, and `cancelled`; a durable draft snapshot includes a stable synthetic receipt marker, cancellation retains the journal, successful target navigation finalizes it, and marker removal preserves existing attachment views in the Composer. Its durable outbox assigns each native share operation one OpenCode-compatible `msg_` message ID before network work; retry, resume, and WebView restoration reuse that ID, while `operationID` remains the native UUID.

Settings uses the standard split-page shell, background, border, spacing, sidebar layout, list rows, and semantic selection state shared by Agents, Providers, and Projects. Its Settings-only selection stays transient. New assistants default to the managed workspace (`workspacePath: null`); registered project options come from `useProjectsStore` and save their canonical paths. A removed project referenced by an existing assistant remains visible as a read-only current-path option until the user chooses a registered or managed workspace. Workspace changes are saved through the Assistant update route, where the server creates and binds the replacement session. Assistant UI contracts and mutation drafts carry no skill-root field.

Focused tests verify desktop and mobile menu order, independent scheduled-task visibility, empty-catalog Settings routing and create-field focus, phone catalog-to-conversation navigation, split Settings structure and responsive workspace selection, removal of topic and skill-root UI, semantic Assistant theme tokens, Assistant secondary surface isolation, and shared `ChatContainer` host / `ChatInput` consumption. Keep standard chat behavior unchanged when extending these shared surfaces.
